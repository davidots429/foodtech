# Business API 인증과 첫 조리 업무 흐름

권고 근거 조회의 선택적 `comparison_id`는 같은 고객이 선택한 현재 비교를 작업·안전·평가 버전과 투입 종료 순서에 대해 다시 확인한다. 두 작업의 읽기 중 변경은 충돌로 처리한다. 선택된 이전 비교는 전체 작업 중 가장 직전이라는 뜻이 아니며, 읽기 뒤 변경 가능성이 있으므로 실제 모델 실행 시 별도 원자적 검증이 필요하다.

권고 근거는 현재 재계산에서 확인된 투입 전 마지막 표본의 온도·시각·경과시간·품질 상태만 반환한다. 표본이 오래되었는지에 대한 합격 기준은 정하지 않았으며 품질 경고도 별도로 표시한다.

완료된 합성 돈까스 작업의 고객은 `POST /api/customer/cooking-jobs/{id}/process-restatements`로 현재 작업 버전과 요청 UUID를 제출해 공정 근거 재계산을 요청할 수 있다. 요청을 조건부 저장한 후 FIFO 큐에 전달하며, 전달 실패 시 같은 UUID로 재시도한다. 상태는 같은 고객의 `GET .../process-restatements/{request_id}`에서 확인한다. 처리 전에 작업 버전이 바뀐 요청은 `STALE`로 종료하므로 최신 근거를 조회한 뒤 다시 요청한다. `FOODTECH_DATA_TABLE`, `FOODTECH_COOKING_TABLE`, `FOODTECH_ORDERED_QUEUE_URL`과 원천 버전 읽기·요청 쓰기·큐 전송 권한이 필요하다. Worker가 처리하지 못하거나 DLQ로 이동한 요청을 자동으로 복구하는 운영 절차는 후속 검증이다.

고객 권고 근거 조회는 현재 작업에 맞는 재계산 결과의 온도 표본 요약을 허용 필드만 반환한다. 오래된 재계산의 요약은 반환하지 않으며, 관찰 표본 요약은 원천 완전성이나 AI 실행 가능성 판정을 대체하지 않는다.

`FOODTECH_DATA_TABLE`이 설정되고 재계산 결과에 스트림 버전이 있으면 권고 근거 조회 전후로 연결된 원본 버전을 강한 일관성으로 읽는다. 조회 시점에 일치한 경우만 `MATCHED_AT_READ`, 바뀌었다면 `CHANGED`, 연결이 다르면 `INCONSISTENT`로 보고한다. 변경·연결 불일치에는 새 권고 요청과 전환 동의를 차단한다. 데이터 테이블 읽기 권한이 필요하며, 일치는 조회 시점과 버전 계약을 따르는 작성자에만 한정되고 AI 실행을 허용하지 않는다.

합성 조리작업의 고객 소유권과 CSRF, 조회된 작업 버전 및 일부 필수 근거를 확인한 뒤 AI 권고 요청·로컬 전환 고지·명시적 동의를 기록할 수 있다. 현재 Tier 1 모델 미설정과 전체 원천 완전성 미평가를 표시하며 이 경로는 AI를 호출하지 않는다. 조리작업 확인과 동의 저장은 별도 트랜잭션이므로 실제 실행 전에는 최신 조리작업 및 전체 근거를 다시 확인해야 한다.

밥 스팀·고등어 건열 조리의 합성 콤비오븐 공통 계산은 `foodtech_contracts.combi_cooking`에 정의한다. 승인된 메뉴별 프로그램 조리시간 경계와 인양을 포함하는 별도 열 노출시간, 밥의 건조·배수 쌀과 추가 물 기반 유효 수분량, 중형 고정 랙·대형 이동식 랙의 서로 다른 정격 하중 및 팬·랙 수 제한을 계산한다. `POST /api/customer/combi-meals`는 고객 범위의 식사 배치와 서로 다른 밥 작업·모드 전환·고등어 작업을 한 트랜잭션으로 만들며 입력 수분비와 적재 한계를 확인한다. `GET /api/customer/combi-meals/{meal_id}`는 본인의 연결 작업을 조회한다. 고객 화면에서 합성 배치 생성과 ID 조회를 제공한다. 모드 전환·고등어 투입·안전 판정은 대기 상태로 시작하며 콤비오븐 Mock과 실제 조리 흐름은 후속 연결 대상이다. 합성 규칙이며 실제 장비·식품 안전기준으로 간주하지 않는다.

`POST /api/customer/combi-meals/{meal_id}/source-observations`는 고객 배치에 C# Mock 원표본 JSONL을 한 번 연결한다. 연결 시 최신 배치 버전을 확인한다. 고객 화면에서 해당 배치와 세 작업 ID가 들어간 Mock fixture를 내려받아 실행하고 생성된 원표본을 선택할 수 있다. 서버는 세 작업의 소유 배치·합성 장비·단계 순서·1초 시각·원천 필드를 확인한 뒤 원표본을 별도 파티션의 100건 단위 항목으로 보존하고 배치 정보·이력과 한 트랜잭션에 기록한다. `GET`으로 같은 경로에 `cursor=0`부터 청크를 조회한다. 원본 바이트 확인용 SHA-256은 단순 줄바꿈 연결 해시이며 표준화 payload 해시와 별도다. 연결 자체는 조리나 공정·안전 결과를 변경하지 않는다. AWS 환경 실검증은 후속이다.

`GET /api/customer/combi-meals/{meal_id}/source-windows?phase=RICE|TRANSITION|MACKEREL&cursor=0`은 고객 소유의 전체 원표본을 다시 읽어 식별자·순번·SHA-256을 검증한 후 해당 구간의 5초 온도 요약을 25개씩 반환한다. 현재·최소·최대·평균과 목표 온도 범위 밖의 초를 표시하고 마지막 5초 미만 구간은 불완전 표본 수와 함께 표시한다. 고객 화면에서 구간과 페이지를 선택해 확인할 수 있다. 결과는 저장된 합성 원표본의 사후 조회이며 실시간 5초 전송이나 안전·공정 판정이 아니다. 조회마다 모든 원표본을 검증하므로 실제 AWS 비용·지연과 대규모 사용 적합성은 미검증이다.

`POST /api/customer/combi-meals/{meal_id}/source-assessment/{rice|transition|mackerel}`은 연결된 원표본의 해시·순서·소유 배치 및 단계 시작시각을 다시 검사한다. 밥·고등어는 조리 기간까지 일치하면 온도·습도 또는 온도·문 부분 판정을 기록한다. 전환은 명시적인 치명 알람·환기 지원·이벤트가 포함된 `synthetic-combi-v2` 표본에서만 준비 조건을 판정하며, 기존 v1 자료의 누락된 값을 추정하지 않는다. 습도는 실측 또는 미지원만 전환 기준으로 사용한다. 결과에는 원본 해시와 사용한 수신 순번 범위를 남기며 화면에서 원표본 시각을 단계 입력에 사용할 수 있다. 안전·품질·종합 판정은 별개다.

`POST /api/customer/combi-meals/{meal_id}/events`는 합성 관찰시각과 기대 버전을 받아 `RICE_STARTED → RICE_PROGRAM_COMPLETED → RICE_UNLOADED → MODE_TRANSITION_STARTED` 순서만 기록한다. 상태·해당 작업·불변 사건은 같은 트랜잭션으로 기록한다. 시간은 과거 순서대로만 입력할 수 있고 밥 프로그램 종료 시 경계별 시간 판정을, 인양 시 열 노출시간을 별도 저장한다. 시간 판정은 온도·습도 등 전체 공정 판정을 대체하지 않는다. 전환 시작은 준비 완료가 아니며 고등어 투입은 차단 상태를 유지한다. 고객 화면의 시각은 합성 수동 기록이고 장비 명령이 아니다.

`POST /api/customer/combi-meals/{meal_id}/transition-evidence`는 합성 전환 시작 이후 연속 1초 표본을 최대 300초까지 받아 온도 215~225°C, 기후 설정 10%, 문 닫힘·치명 알람 없음의 30초 연속 조건을 확인한다. 습도 지원 시 각 표본의 습도 15% 이하도 필요하고, 미지원 시 180초 경과와 지원되는 환기 플랩의 열림·닫힘 순서를 요구한다. 이전 표본과 센서 지원 여부는 변경할 수 없다. 300초 내 통과하면 `DRY_HEAT_READY`, 그렇지 않으면 `MODE_TRANSITION_TIMEOUT`으로 기록한다. 습도 미지원 상태와 근거는 별도 기록하며 실제 습도 충족으로 표현하지 않는다. 고객 화면은 지정된 정상 합성 표본을 생성해 이 경계를 시험한다. 전환 검증은 고등어의 조리·안전 판정이 아니며 실제 장비 제어를 수행하지 않는다.

전환 준비 이후 합성 고등어 작업의 투입·프로그램 완료·인양을 순서대로 기록하며 조리시간과 열 노출시간을 분리한다. 제품은 토막당 120~150g, 두께 1.5~2.0cm 범위를 적용한다. `POST /api/customer/combi-meals/{meal_id}/mackerel-safety`는 인양 즉시 시작된 서로 다른 제품·탐침의 연속 60초 표본을 확인한다. 한 랙의 세 선반 이상은 상·중·하, 두 선반은 무거운 단 두 개와 다른 단 한 개, 한 선반은 좌·중·우를 선택한다. 선반 번호는 클수록 위쪽이며 가장 두꺼운 제품 선택과 위치 증거도 해당 기준에 따라 확인한다. 한 선반의 제품이 3개 미만이면 전수 검사한다. 대형 두 랙은 각각 표본을 포함하고 더 무거운 랙에서 두 개를 선택한다. 랙 무게가 같으면 상·중·하 위치를 가능한 범위에서 최대한 포괄하고 선정 근거를 남긴다. 선정 조건이 미충족이거나 확인 불가하면 이력의 `selection_issues`에 남기고 통과시키지 않는다. 교정된 값이 하나라도 75°C 미만이면 `FAILED`, 표본 누락·교정 만료는 `ASSESSMENT_INCOMPLETE`, 모두 유효하고 75°C 이상이면 `PASSED`와 최저값을 남긴다. 이력은 새 사건으로 보존하고 실패 후 추가 가열·재검증은 별도 구간과 안전 이력으로 기록한다. 이 판정은 안전 표본에 한정된다.

`POST /api/customer/combi-meals/{meal_id}/mackerel-process`는 조리시간 전체에 해당하는 최대 900개의 1초 합성 챔버 온도·문 표본을 받는다. 최초 적재 후 문 닫힘이 2초 확인된 시점부터 120초 이내 215~225°C 30초 유지, 복원 후 200°C 미만 30초 지속, 활성 조리 중 2초 문 상태 확정 및 누적·연속 개방 경계와 시간 판정을 계산한다. 관찰·확정 초와 원표본을 보존하고 안전 결과와 별도로 부분 판정을 기록한다. 최종 표본에서 문 상태가 확정되지 않은 경우 미완료로 남긴다. 기후·팬 등 다른 공정 항목과 종합 판정은 후속 범위다.

`POST /api/customer/combi-meals/{meal_id}/rice-process`는 밥 조리 전체의 1초 합성 온도·습도·문 표본을 최대 2,000초까지 검사하고 원표본과 부분 판정을 기록한다. 저온·고온 연속 및 누적 지속시간, 습도 경고·스팀 부족 경계, 2초 문 상태 확정과 시간 판정을 적용한다. 문 표본이 전부 없는 이전 요청은 문 미측정으로 기록하며 정상으로 판정하지 않는다. 고온 급변은 센서 이상 의심으로 남기고 해당 값을 공정 타이머에서 제외하지 않는다. 습도 출처는 실측·제어기 추정·미지원으로 구분하며 미지원은 정상으로 취급하지 않는다. 팬 심각도와 종합 공정판정, 센서 이상 확정·품질 격리는 후속 범위다.

밥·고등어 공정에서 팬 단계가 일부라도 누락되거나 목표와 다르면, 이미 확인된 공정 실패가 없는 한 결과를 `INSUFFICIENT_DATA`로 둔다. 목표와 다른 값은 `FAN_DEVIATION`으로 기록하며 별도의 팬 실패 임계치를 추정하지 않는다. 밥 안전 확인에는 팬 단계 관찰이 전체 구간에서 목표와 일치해야 한다. 팬 근거가 없는 과거 밥 안전 합격과 품질평가는 이력을 유지하되 현재 조회·새 평가에서 사용하지 않는다.

`POST /api/customer/combi-meals/{meal_id}/rice-preparation`은 밥 조리 시작 전 합성 세척 횟수, 불림물 온도, 불림·배수 시각과 선택적인 세척·불림 후 중량을 기록한다. 기존 건조 쌀과 배수 후 중량은 식사 배치 생성값으로 유지한다. 시각 순서와 배수 완료 후 조리 시작을 검증하고 수정 사유와 이전 기록을 남긴다. 선택 중량을 생략하면 기존 값을 유지하고 `null`은 해당 값을 지운다. 합성 기준은 세척 3회·약 20°C·불림 30분·배수 5분이지만 기록만으로 적합성이나 안전을 판정하지 않는다.

고객의 합성 외부 AI 시험은 `/api/customer/ai/external/preview`에서 모델·자격증명 ID를 보내 견적을 받고, 표시된 외부 전송과 비용 가능성에 명시 동의한 경우에만 `/api/customer/ai/external/quotes/{id}/confirm`으로 실행한다. 두 요청 모두 고객 세션과 CSRF를 검사하고 tenant ID는 서버 세션에서만 가져온다. `/api/customer/ai/executions/{id}/status`는 확인 요청이 끊긴 경우 결과를 다시 읽는다. 업무 API는 Gateway에 고정된 합성 질문의 내용이나 저장된 API 키를 받지 않는다. ## 구현 경계

- 로그인 흐름과 세션은 DynamoDB 테이블이 지정되면 공유된다. 비어 있으면 로컬 개발용 메모리 저장소를 사용하며 재시작 시 로그아웃된다. DynamoDB TTL 삭제는 비동기이므로 API는 모든 읽기에서 만료 시각을 직접 검사한다.
- 세션은 최장 1시간이고 Access 토큰 만료를 넘지 않는다. 고객 TOTP 등록용 Access 토큰과 관리자 인증 챌린지 세션은 브라우저에 노출하지 않고 공유 저장소에 만료 시각과 함께 저장한다. 등록 키는 등록 요청의 응답으로만 전달하고 저장하지 않는다. 관리자 화면의 비밀번호와 TOTP 값은 Cognito 인증 요청에만 사용하고 로그나 저장소에 기록하지 않는다. 공개 배포에는 HTTPS가 필수다. 프로젝트 관리자의 `POST /api/admin/users/{subject}/revoke-admin`과 `POST /api/admin/users/{subject}/suspend`는 CSRF를 확인한 뒤 공유 저장소의 차단 상태와 권한 버전을 변경한다. 기존 세션은 다음 API 요청부터 거부되며 새 관리자 로그인 또는 이용 중단 계정의 로그인도 거부된다. 이 조치는 애플리케이션 접근을 차단하며 Cognito 그룹·계정 상태 자체를 변경하지 않는다.
- 보호 API 요청마다 Cognito의 현재 계정 활성 상태를 확인하고 관리자 요청에는 현재 그룹도 확인한다. Cognito 호출에 실패하면 접근을 허용하지 않는다. 이 방식은 요청마다 Cognito API 호출과 지연을 추가하므로 부하 시험에서 조정해야 한다. 갱신은 별도 KMS 키·역할 권한과 실제 Cognito 설정의 검증이 필요하며 실제 공개 서비스용 인증 완료로 취급하지 않는다.
- 무료 예시 API는 공용 합성 자료만 읽기 전용으로 반환한다. 합성 조리작업·평가와 시연용 티어 전환 신청은 별도 고객 범위에 저장한다. 매장별 범위·권한 모델과 무료 AI 모델의 자동 제공은 후속 기능이다.

세션 갱신은 `FOODTECH_AUTH_REFRESH_KEY_ARN`과 `FOODTECH_ENVIRONMENT`가 구성된 경우에만 새 로그인부터 활성화된다. 갱신 토큰은 서버에서 AWS Encryption SDK의 key commitment와 세션별 암호화 컨텍스트로 보호한다. 고객·관리자 화면과 콤비 합성 수집은 만료 전에 CSRF 보호 갱신을 요청한다. 갱신 중 로그아웃·경쟁을 조건부 쓰기로 차단하고 최대 세션 수명은 로그인부터 8시간이다. 브라우저 재접속 시 액세스 토큰이 만료되어도 유효한 서버 세션과 권한이 있으면 캐시하지 않는 CSRF 문맥을 받아 갱신한다. 서버 세션의 최대 수명이 끝나거나 권한이 회수되면 재로그인이 필요하다. 로그아웃은 서버 세션을 먼저 삭제하고 Cognito 토큰 회수를 시도하며 `cognitoTokenRevoked`로 성공 여부를 구분한다. 갱신 중 세션이 삭제되어 새 토큰 저장에 실패하면 해당 토큰의 회수도 시도하지만, 네트워크·프로세스 장애 중 회수 성공은 보장하지 않는다. 기존 시험 Cognito 고객 계정과 개발 DynamoDB·KMS를 사용해 로그인, 갱신, 갱신 후 세션 조회, 토큰 회수와 로그아웃 후 접근 거부를 확인했다. 같은 시험 계정에 관리자 그룹을 일시 부여해 비밀번호·TOTP 로그인 이후 동일한 갱신·회수를 확인하고 관리자 권한 제거를 검증했다. 해당 시험 App Client는 토큰 회전이 꺼져 있었으므로 회전 활성 상태, 전용 KMS 키 정책과 배포 역할은 아직 실검증하지 않았다. KMS 시험에는 기존 개발 키를 임시 사용했으며 배포 키나 역할을 검증한 결과는 아니다. 설정이 없거나 이전 세션이면 기존 만료 동작을 유지한다.
- 2026-11-01 AWS Free Plan의 시험용 Cognito User Pool에서 고객 가입·이메일 확인·Authorization Code/PKCE 토큰 교환·고객 세션·관리자 그룹 거부·로그아웃 후 API 거부를 확인했다. Cognito 관리형 로그인 v2는 시험 계정에서 동작했다. 시험 리소스는 아직 CDK 관리 대상이 아니다.
- 같은 시험 계정으로 DynamoDB 공유 저장소를 연결해 다시 로그인했다. 세션 생성, API 프로세스 재시작 후 로그인 유지, 로그아웃 후 세션 제거를 실제 AWS 테이블에서 확인했다.
- 시험 Pool의 관리형 로그인은 TOTP를 완료해도 토큰에 `acr`·`amr`를 넣지 않았다. 관리자 App Client의 직접 인증 경로에서 Cognito `SOFTWARE_TOKEN_MFA` 챌린지 성공 후 관리자 화면 진입을 확인했다. 시험용 관리자 그룹을 즉시 회수하고 다음 화면 요청에서 접근이 거부되는 것도 확인했다. Pool MFA는 `OPTIONAL`을 유지한다.

## 돈까스 합성 조리작업 첫 흐름

`/api/customer/cooking-jobs`는 고객 세션의 `subject`에서 저장 범위를 만들고 상태 변경 요청마다 CSRF와 기대 `version`을 검사한다. 첫 범위는 합성 튀김기 `synthetic-fryer`의 돈까스 작업이다. 생성, 승인된 수동 상태 전이, 심부온도 안전 확인, 안전 이상·해제, 완료 품질평가, 평가 이력과 재조리 연결을 제공한다. 연결된 합성 배치의 표준화된 온도값에 대해서는 자동 공정판정을 수행한다. 고객이 `PROCESS_FAILURE_DETECTED`를 임의로 제출하는 API는 제공하지 않는다.

`POST /api/customer/ai/cooking-chat`은 고객이 소유한 조리작업의 버전·합성 메뉴·작업/안전/공정/시간 상태와 유효한 품질 합격 여부만 구조화된 사용자 메시지에 담아 로컬 모델에 전달한다. 원본 표본·소유자 ID·자유 메모는 전달하지 않는다. 차단되었거나 안전 버전이 맞지 않는 평가는 미확인으로 전달하고, 늦은 수집값의 파생 판정이 있으면 해당 판정과 작업 버전 변경 여부를 함께 표시한다. 이 상담은 조회 시점의 설명이며 설정값 검증·안전 판정·후보 레시피 생성을 수행하지 않는다. 시스템 역할 분리는 모델 출력을 안전한 권고로 보장하지 않으므로 운영자가 검토해야 한다.

2026-11-21에는 `AWS_PROFILE=foodtech FOODTECH_OLLAMA_BIN=<ollama 실행파일> .venv/bin/python tests/live/cooking_context_ollama_check.py`로 합성 고객 세션·개발 DynamoDB 작업과 실행 기록·실제 루프백 mTLS Gateway·로컬 `llama3.1:8b`를 결합했다. 작업 맥락과 식별자 제외, 응답 저장, 모델 종료 후 실패 기록, 호출 한도 및 시험 항목 정리를 확인했다. 모델 출력의 정확성·안전성, 실제 Cognito·배포 환경과 서버 GPU 성능은 이 시험 범위가 아니다.

돈까스 합성 심부온도 입력은 화면과 API 모두 -273.15~300°C로 제한한다. 범위 밖 입력은 판정이나 작업 버전을 변경하지 않는다. 이 범위는 합성 입력의 기술적 제한이며 식품 안전 허용 범위가 아니다.

안전 확인은 계획 인분마다 독립 탐침의 0~60초 1Hz 합성 시계열 61개를 요구한다. 모든 유효 표본이 `75°C` 이상이면 `PASSED`, 유효 표본 하나라도 미달하면 `FAILED`, 시간축·필수값·교정 유효성이 부족하면 `INCOMPLETE`다. 이상 의심·확인 중·실패에서는 평가를 완료할 수 없다. 의심 해제나 새 안전 확인만으로 기존 합격 평가를 다시 사용 가능하게 만들지 않으며, 새 완료 평가가 필요하다. 작업 상태·안전 상태의 변경과 근거는 `EVENT#...` 이력에 현재 상태 변경과 함께 원자적으로 기록한다.

품질평가는 초기 공통 척도 `tonkatsu-common-v1`의 7개 항목 모두에 1~5점과 관찰 근거를 요구한다. `해당 없음`은 이 첫 척도에 없다. 종합점수는 합계/35×100이며 모든 항목이 3점 이상일 때 합격, 4점 이상일 때 목표 달성이다. 수정·재평가는 사유와 이전 버전을 기록하고 원본을 보존한다. 새 버전과 `ASSESSMENT#CURRENT` 포인터는 같은 DynamoDB 트랜잭션으로 기록하며 작업 `version` 충돌을 거부한다.

`FOODTECH_COOKING_TABLE`이 비어 있으면 로컬 메모리 저장소를 사용한다. 공개 배포에서는 별도 DynamoDB 테이블이 필수다. DynamoDB 숫자형을 API의 정수형으로 정규화한다. 실사용 규모·성능과 배포된 API 실행 역할은 검증하지 않았다. 고객 화면은 생성·상태·안전·평가·재조리를 연결한다. `GET /api/customer/cooking-jobs`는 고객 세션 범위의 생성 정보만 최신순으로 최대 50건씩 조회하고 `next_cursor`로 다음 페이지를 연다. 신규 작업과 재조리는 메타데이터와 목록 항목을 한 트랜잭션에 저장하므로 추가 인덱스·테이블 배포가 필요 없다. 작업 상태는 목록에 중복 저장하지 않고 상세 조회에서 확인한다. 이전 형식의 작업은 고객이 기존 ID로 열 때 `POST /api/customer/cooking-jobs/{job_id}/list-entry`로 목록에 등록한다. 이 등록은 소유권과 CSRF를 검사하며 반복해도 목록 항목을 늘리지 않는다.

## 합성 수집 배치와 자동 온도 공정판정

`equipment_profile="jeyuk-small"`로 생성하는 제육볶음 합성 작업은 실제 투입량(kg)을 받으며 1.8kg 권장량을 넘으면 경고, 3.0kg 정격량을 넘으면 생성을 거부한다. 조리 시작 전 `synthetic-rest / mockprofile-110-a-001 / jeyuk-...` fixture를 작업 하나에 연결한다. Worker가 연결된 원표본의 표면온도·교반 RPM·모터 부하 판정을 반영하고 실패가 확정되면 작업을 `FAILED`로 전이해 평가를 차단한다. 돈까스 두께·탐침·평가 입력 계약을 제육볶음에 적용하지 않는다. 2026-11-15 개발용 AWS에서 합성 원표본 30건의 5초 걸림 경고, 30초 실패, 작업 실패 전이와 재전달 시 중복 변경 방지를 확인하고 시험 항목을 정리했다. 재실행 명령은 `AWS_PROFILE=foodtech .venv/bin/python tests/live/jeyuk_job_dynamodb_check.py`다.

삭제 체크포인트 복구자는 암호화 시 사용한 원본 테이블 ARN을 지정해야 한다. 테이블 ARN은 KMS 키와 동일한 계정·리전이어야 하며, 신뢰된 작업자가 실제로 읽을 테이블과 이 ARN이 일치하는지 확인하는 연결은 별도로 필요하다.

GuardedDeletion의 내부 복구 조회는 인증·Vault·Capsule·삭제 등록을 하나의 DynamoDB 트랜잭션으로 읽고 동일 사용자 연결과 요청 잠금, 등록 상태·암호문 존재를 대조한다. 정상 시 비밀값 없는 `DELETING`만 반환한다. 개발 DynamoDB 합성 시험에서 정상 복구와 다른 요청 거부를 확인했다. 신뢰된 식별자 복구·호출자 인증, 삭제 진행 재개와 실제 권한 검증은 별도다.

삭제 등록부 복구 전용 암호화 경계는 별도의 복구 호출자가 요청 ID와 필드별 문맥을 확인하고 내부 ID·Capsule locator를 제한된 콜백에서만 사용한다. 변경 가능한 버퍼는 성공·실패 시 덮어쓰지만 Python 및 SDK의 모든 복사본을 지울 수는 없다. 잠금 복구 조회는 내부 ID도 Vault와 대조한다. 개발 KMS와 DynamoDB에서 각각 합성 왕복 및 잠금 복구를 확인했으며 호출자 인증, JIT 복호화 역할과 두 구성요소의 서비스 연결은 남아 있다.

내부 GuardedDeletionRecovery는 인증된 사용자와 요청으로 서버의 인증·등록 기록을 읽고 복구 전용 암호화 경계에서 식별자를 연 뒤 네 영역 잠금을 다시 확인한다. 식별자를 요청 입력이나 응답으로 사용하지 않는다. 개발 KMS·DynamoDB에서 합성 등록부터 복구까지 확인했다. 이 클래스 자체는 인증·인가, JIT 역할 발급이나 실제 삭제 재개를 구현하지 않는다.

내부 복구의 `use_locked`는 네 영역의 잠금을 확인한 뒤 신뢰된 작업 콜백에서만 복구된 식별자를 사용하고 상태만 반환한다. 개발 AWS에서 합성 요청 복구 뒤 잠금된 빈 Capsule 인벤토리 조회를 연결해 확인했다. 잠금 확인은 이후까지 잠금을 유지하지 않으므로 모든 변경은 자체 원자적 잠금 검사가 필요하다. 인증·JIT 역할·전체 삭제 재개는 아직 제공하지 않는다.

개발 AWS 합성 통합 시험에서는 사용자별 래핑 키와 암호화된 Capsule 항목을 만든 뒤 삭제 잠금·등록·복구를 거쳐 같은 항목의 삭제 대상 계획을 생성하고 시험 레코드를 정리했다. 실제 저장소 삭제·백업 처리나 고객별 실행 역할은 이 시험의 범위가 아니다.

Capsule 사용자 키 META에는 tenant 범위의 목적·기간·HMAC 키 버전도 키 부착 시 함께 기록한다. 내부 ID와 가명 digest는 이 필드에 넣지 않는다. 인벤토리는 해당 값의 형식과 조회 전후 일관성을 확인하고 하나라도 누락된 키 메타데이터를 거부한다. 기존 형식의 키가 있는 Capsule은 그대로 복구되지 않으며 신뢰 가능한 범위 확인과 이전 절차가 필요하다. 내부 복구 경계의 잠금된 인벤토리에서 저장된 범위와 내부 ID로 tenant를 재계산해 삭제 계획을 만드는 경로를 제공한다. 인증된 실행 서비스와 계획 영속화는 아직 남았다.

신규 조리 조건 프로파일은 원본과 사용자별 `CONDITION_PROFILES` 참조 항목을 같은 DynamoDB 트랜잭션으로 저장한다. 내부 페이지 조회는 사용자별 참조만 읽는다. 확인된 기존 프로파일은 원본의 ID·버전을 조건 검사하는 트랜잭션으로 참조를 멱등하게 보충할 수 있다. 기존 프로파일 목록 보충은 정지·삭제 잠금을 원본 검사 및 참조 저장과 같은 트랜잭션에서 검사한다. 잠금 중에는 보충할 수 없으며 잠금을 유지한 채 삭제 대상 전수를 확인하는 별도 승인된 절차가 아직 없다. 이 목록과 스캔 완료는 전체 삭제 대상의 증거나 삭제 완료 조건으로 사용할 수 없다. 기존 레코드의 전수 발견·보충과 모든 작성자의 잠금 강제가 필요하다.

기존 조건 프로파일 전수 발견을 위한 내부 유지보수 경로는 테이블의 강한 일관성 Scan을 제한된 페이지로 수행하고 소유자에 일치하는 원본만 검증해 참조를 보충한다. 필터 결과가 비어 있어도 체크포인트가 있으면 다음 페이지가 필요하다. 체크포인트에는 다른 사용자의 테이블 키가 포함될 수 있으므로 고객에게 반환하거나 로그에 남기지 않고 별도 권한과 보호된 저장소에서만 다룬다. 부분 실패는 같은 체크포인트로 재시도한다. 여러 페이지 Scan은 일관된 스냅샷이 아니므로 쓰기 잠금·재확인과 복구 절차가 없으면 완료 증거가 아니며 API나 자동 실행에는 연결하지 않았다.

내부 `ProfileCheckpointCipher`는 Scan 체크포인트와 소유자 범위를 AWS Encryption SDK와 서버가 지정한 KMS 키로 암호화하고 무작위 작업 ID·환경·목적을 인증 문맥에 결합한다. 별도 개발 키에서 합성 체크포인트의 복호화·다른 작업 ID·다른 소유자 및 변조 거부를 확인했다. 암호문 저장과 체크포인트 갱신, 운영 KMS 키·별도 역할·IAM 경계는 아직 연결되지 않았으며 Python/SDK 내부 복사본의 완전한 메모리 삭제는 보장하지 않는다.

내부 `ProfileScanProgressStore`는 사용자 범위를 암호화한 체크포인트를 별도 작업 레코드에 두고, 한 페이지의 참조 보충이 모두 끝난 다음 기대 phase·version 조건으로 진행 위치를 갱신한다. 실패 또는 경합 시 같은 페이지를 다시 처리한다. 응답 유실 후에는 소유자와 암호문을 검증한 뒤 체크포인트 원문 없이 phase·version만 확인한다. `SCAN_COMPLETE`는 한 번의 Scan이 끝났다는 뜻이며 잠금·동시 쓰기 확인이나 삭제 완료를 뜻하지 않는다. 개발 테이블·KMS에서 합성 작업의 저장·소유자 검증·페이지 전진·정리를 확인했다. 실제 전용 작업 테이블·KMS·실행 역할 및 인증된 운영 경로는 아직 구성하지 않았다.

체크포인트는 원본 테이블 ARN에도 결합하고 Scan 원본과 참조 보충 저장소의 실제 ARN이 다르면 중단한다. 운영 역할과 IAM 권한 경계는 별도 검증해야 한다.

DynamoDB 조리 조건 프로파일·조리작업 신규 생성과 재조리는 인증 테이블의 현재 세션 epoch·정지 상태·삭제 잠금을 원본·목록 생성과 같은 트랜잭션에서 검사한다. 재조리는 원본과 새 작업의 소유 범위도 확인한다. 인증 테이블 설정이 없으면 해당 쓰기는 거부한다. 이 문장의 조건은 세 생성 경로에 적용되며 다른 조리·AI 작성 경로는 각각 별도로 검사해야 한다. DynamoDB 권한에는 인증 테이블의 조건 검사 권한도 필요하며 배포 역할로 아직 검증하지 않았다. 메모리 저장소는 실제 인증 테이블과의 경쟁을 재현하지 않는다. 개발용 DynamoDB 조리 생성 시험에서도 `FOODTECH_AUTH_TABLE=foodtech-auth-sessions-dev` 설정이 필요하다.

고객이 공통 `commit` 경로로 기록하는 조리 상태 전이·수동 안전 확인·평가 변경은 세션 epoch·정지·삭제 잠금을 작업 본문 및 이벤트·평가·현재 포인터 저장과 같은 트랜잭션에서 검사한다. 개발 DynamoDB에서 잠금 중 평가 포함 변경 전체가 거부되고 잠금 해제 후 저장되는 것을 합성 작업으로 확인했다. 고객의 수집 배치 연결도 같은 인증 조건을 연결 레코드·작업 버전과 함께 검사한다. 별도 쓰기 경로는 이 보호를 자동으로 상속하지 않으므로 각 경로에서 검사해야 한다.

평가 집계와 비교 결과의 저장 및 기존 결과의 목록 복구는 동일 소유자의 선택 작업만 허용하고 인증 테이블의 정지·삭제 잠금을 같은 트랜잭션에서 검사한다. 고객 요청은 세션 epoch도 검사하고 비동기 파생 갱신은 잠금 상태를 검사한다. 개발 DynamoDB에서 합성 집계와 비교 결과의 잠금 거부·정상 저장·멱등 복구·재잠금 거부를 확인했고, 비교에서는 세션 epoch 불일치도 거부했다. 그 밖의 파생 쓰기 경로의 잠금은 별도로 확인해야 한다.

제육 공정 검증 근거 스냅샷도 고객 세션 epoch·정지 상태·삭제 잠금을 원본 작업·수집 영수증·프로파일 조건 및 저장과 같은 트랜잭션에서 확인한다. 개발 DynamoDB의 합성 데이터로 잠금·오래된 epoch의 쓰기 거부와 정상 저장을 확인했다. 고객 재평가 신규 요청과 이력 저장도 같은 트랜잭션에서 세션 epoch·정지·삭제 잠금을 검사한다. 기존 요청 조회와 SQS 전송은 원자적으로 묶이지 않으며 잠금과 큐 전송의 경쟁 및 기존 큐·DLQ 정리에는 별도 처리가 필요하다.

밥·고등어 식사 배치 생성, 단계·안전·품질 변경, 수집 원천 연결과 실시간 원천 추가는 고객 세션 epoch·정지·삭제 잠금을 해당 쓰기와 같은 트랜잭션에서 검사한다. 개발 DynamoDB 합성 시험에서 잠금 중 네 경로의 쓰기 거부와 잠금 해제 후 정상 처리를 확인했다. 이는 전체 고객 데이터 삭제 완료를 의미하지 않으며 배포 역할의 인증 테이블 접근은 별도 검증이 필요하다.

신규 식사 배치는 사용자별 `COMBI_MEALS` 참조도 생성 트랜잭션에 저장하며 내부 목록은 사용자별로 일관성 있게 페이지 조회한다. 기존 배치는 목록에 없을 수 있다. 확인된 기존 배치는 원본 ID·정지·삭제 잠금을 검사해 멱등하게 참조를 보충할 수 있지만, 전수 발견 및 잠금 중 삭제 대상 확인 절차는 아직 없으므로 삭제 완료를 보장하지 않는다.

기존 식사 배치 후보는 내부 제한 Scan으로 사용자 범위를 검증하며 페이지별로 찾아 목록을 보충할 수 있다. Scan의 원시 체크포인트는 다른 사용자의 키를 포함할 수 있어 외부에 반환하거나 로그에 남기면 안 된다. 식사 배치 Scan은 프로파일과 분리된 암호화 목적·저장 키를 사용하는 진행 저장을 지원한다. 개발 KMS·DynamoDB의 합성 시험은 통과했지만 전용 키·테이블·호출 권한 경계와 잠금 중 삭제 대상 확인은 아직 없으며, Scan 종료는 일관된 전체 스냅샷이나 삭제 완료의 증거가 아니다.

식사 배치 정리를 위한 내부 구성요소는 암호화된 대상 페이지를 전부 검증한 뒤 선택된 배치의 잠금·활성 삭제 요청·사용자 범위 META를 같은 트랜잭션에서 검사하고 META 외 기록을 한 건씩 삭제한다. Scan은 일관된 스냅샷이 아니며 대상 전수 확인과 인증된 작업자 배포, 목록·META 정리 및 원천 데이터 처리는 남아 있다. 실제 AWS 검증도 하지 않았다. META만 남았다는 관찰은 삭제 완료 증거가 아니다.

별도 내부 목록 정리는 해당 식사 배치 파티션이 비어 있는지 일관 읽기로 확인한 뒤 잠금·활성 요청·META 부재를 트랜잭션에서 확인해 목록 참조를 제거한다. 조회와 삭제 사이에 META 외 기록이 새로 생기지 않도록 모든 쓰기 중지와 별도 잔여 검사가 선행돼야 한다. 이 구성요소는 전체 삭제 흐름에 연결되지 않았고 실제 AWS 검증도 남아 있다.

식사 배치 전용 잔여 Scan은 META가 없는 고아 기록과 META를 포함한 최종 잔여 기록을 각각 감지하고, 잔여 발견 시 해당 위치에서 중단한다. 진행 상태는 기존 잠금·암호화 저장 계약을 사용한다. 이 관찰은 스냅샷이나 삭제 완료 증거가 아니며 인증된 작업자·전체 흐름 연결·실제 AWS 검증은 남아 있다.

식사 배치 META 정리 구성요소는 META 외 잔여 Scan이 끝난 대상에 대해 파티션에 META만 남았는지 확인하고, 원천 정보를 포함한 전체 META를 암호화된 진행 기록에 보존한 후 잠금·활성 요청·배치 ID·버전을 검사해 삭제한다. 쓰기 중지 증명, 원천 소유권 검토, 최종 잔여 검사와 전체 삭제 흐름 연결 및 실제 AWS 검증은 남아 있다. 보존본 삭제·백업 처리도 별도다.

내부 식사 배치 조정기는 대상 수집 → 기록 정리 → 잔여 확인 → META 보존·정리 → 목록 정리 → 최종 잔여 확인 → 보존된 원천 확인을 재개 가능하게 연결한다. 원천 정보가 있으면 소유권 확인 필요 상태에 머물며 식별자를 반환하지 않는다. 인증된 작업자와 전체 계정 삭제 Saga에는 연결되지 않았고 `VERIFYING`은 삭제 완료가 아니다. 작성자 중지 증명과 실제 AWS·백업 검증은 별도로 필요하다.

개발 DynamoDB·KMS에서 선행 개인정보 삭제 진행 저장 모듈과 함께 합성 식사 배치의 단계 연결, 원천 소유권 확인 중단, 다른 고객 기록 보존 및 시험 데이터 정리를 확인했다. `tests/live/meal_deletion_coordinator_check.py`는 개발 프로파일과 명시적 실행 변수가 필요하다. 이 검증은 개발자 자격증명을 사용했으며 배포된 작업자 역할이나 백업 복원 검증이 아니다.

식사 배치 조정기는 삭제 요청 복구 경계를 통해 호출할 수 있으며 요청 소유자와 활성 잠금을 확인한 후 한 단계만 실행한다. 개발 DynamoDB·KMS의 합성 요청 등록부터 식사 배치 정리까지 연결하고 다른 사용자 거부 및 시험 데이터 정리를 확인했다. 이 내부 경계 자체는 호출자 인증이 아니며 배포된 작업자와 전체 삭제 완료 검증은 남아 있다.

내부 조리 삭제 복구는 조건 프로파일 → 조리작업 → 식사 배치 순서를 갖지만, 이전 작성자의 중지 증명이 아직 연결되지 않아 현재는 `QUIESCENCE`에서 정리 실행을 차단한다. 이 차단을 추가하기 전 개발 DynamoDB·KMS 합성 요청에서 각 영역과 연결 순서를 확인했다. 개별 내부 구성요소는 별도 호출자 인증 및 작성자 중지 조건이 필요하다. 계정 삭제 완료는 표시하지 않으며 다른 저장소·보존본·백업과 배포 작업자 검증도 남아 있다.

각 영역의 내부 요청 복구 어댑터를 직접 호출해도 요청 소유자·잠금을 확인한 뒤 작성자 중지 증명이 없으면 `QUIESCENCE`로 중단한다. 더 낮은 수준의 저장소 구성요소는 공개 호출 경계가 아니며 직접 실행 전 별도 인증·중지 검증이 필요하다. 기존 통합 실환경 시험은 작성자 중지 증명이 구현될 때까지 실행을 시작하지 않는다.

식사 품질 집계는 그룹 목록에 의존하지 않고 고객 범위의 결과 행을 제한 Scan과 암호화 진행 기록으로 수집한다. 전체 수집 페이지 검증 후 활성 잠금 아래 결과를 개별 정리하고 결과 파티션이 빈 그룹 목록만 제거하는 내부 구성요소가 있다. 별도 잔여 Scan은 예상하지 못한 행도 탐지해 중단한다. 이 구성요소들은 아직 전체 삭제 조정기·호출자 인증에 연결되지 않았고 쓰기 중지 증명, 실제 AWS·백업 복원 검증이 필요하다.

식사 품질 집계의 대상 수집·결과 정리·그룹 정리·잔여 검사·최종 그룹 검사는 재개 가능한 내부 조정기로 연결되며 조리 삭제 복구의 필수 단계다. 이전 형식의 조리 `VERIFYING` 체크포인트도 집계 단계를 다시 거친다. 현재 작성자 중지 증명이 없어 복구 경계와 집계 조정기는 `QUIESCENCE`에서 차단한다. 호출자 인증·실제 AWS 작업자·다른 저장소와 백업 복원 검증은 남아 있으며 로컬 단계 시험의 중지 증명은 모의다.

`tests/live/meal_aggregate_deletion_dynamodb_check.py`로 개발 DynamoDB·KMS의 합성 결과 두 건을 목록과 독립적으로 발견하고 비활성 요청 거부, 결과·빈 그룹 정리, 잔여 관찰과 다른 고객 보존을 확인했다. 시험 데이터와 진행 기록은 정리했다. 개발자 자격증명으로 개별 구성요소를 시험했으며 작성자 중지, 배포 작업자 인증·권한, 전체 삭제 또는 백업 복원을 증명하지 않는다.

식사 배치 삭제 잠금·목록 변경 후 개발 DynamoDB에서 밥 안전·품질 재평가, 원천 경계 재판정, 실시간 수집 및 C# Mock 연동 시험을 재실행했다. 각 합성 고객의 배치·원천·사용자별 목록 정리를 확인했다. C# Mock 빌드는 로컬 패키지 캐시를 사용했고 네트워크 제한으로 NuGet 취약점 조회는 수행하지 않았다.

내부 삭제 작업은 확인된 조건 프로파일 버전과 그 목록 참조를 같은 고객의 일치하는 삭제 잠금·정지 상태 아래 한 트랜잭션으로 삭제한다. 두 행의 ID·버전이 다르면 둘 다 지우지 않으며 이미 삭제된 행에 대한 재시도도 허용한다. 개발 DynamoDB에서 잘못된 요청·참조 변경 거부, 다른 버전 보존 및 합성 항목 정리를 확인했다. 기존 프로파일의 전체 스캔·암호화 진행 상태·인증된 작업자 연결, 작업·다른 저장소·백업 잔존 검증은 별도다.

시연 티어 신청은 인증 테이블의 고객 세션 epoch·정지·삭제 잠금을 신청 기록과 같은 트랜잭션에서 검사한다. 관리자 심사는 신청 고객의 정지·삭제 잠금과 심사자의 세션 epoch·정지·삭제 잠금을 함께 검사하며 같은 계정이면 한 번만 검사한다. `FOODTECH_AUTH_TABLE`과 인증 테이블 `dynamodb:ConditionCheckItem` 권한이 필요하다. 개발 시험은 기존 조리 테이블의 격리된 합성 키를 사용했으며 전용 티어 테이블·배포 역할과 사용자 삭제의 전체 완결성을 검증한 결과는 아니다. 메모리 저장소는 실제 삭제 잠금 경쟁을 재현하지 않는다.

티어 데이터의 내부 삭제 대상 탐색은 고객별 `TENANT` 파티션을 강한 일관성으로 페이지 조회하고 기본 키만 반환한다. 현재 신청, 과거 신청, 심사 기록과 예상하지 못한 키도 빠뜨리지 않고 발견하기 위한 내부 구성요소다. 내부 삭제는 인증 테이블의 일치하는 삭제 요청 잠금을 같은 트랜잭션에서 확인한다. 제한된 페이지 처리 중 실패하면 첫 페이지부터 다시 조회하며 이미 삭제된 항목은 건너뛴다. 빈 페이지는 그 시점의 관찰일 뿐 전체 삭제 완료를 뜻하지 않는다. 호출 주체 인증·전체 삭제 작업 연결·GSI 반영 대기·백업 잔존 확인 및 복원 후 재삭제는 별도로 구현해야 하며, 목록 조회나 단건 삭제 성공은 삭제 완료가 아니다.

관리자 티어 대기 목록은 지연될 수 있는 보조 인덱스의 후보마다 기본 테이블의 현재 신청과 인증 테이블의 정지·삭제 잠금을 강한 일관성으로 다시 확인한다. 한 번에 최대 10개 인덱스 페이지를 살펴 결과가 한도보다 적을 수 있고, 조회 직후의 상태 변경과 완전히 원자적인 화면 노출 방지는 보장하지 않는다. 심사 쓰기는 관리자 권한 차단도 별도로 트랜잭션에서 확인한다. 목록의 실제 GSI 지연 및 서비스 역할 `GetItem` 권한은 전용 티어 테이블 배포 후 검증해야 한다.

개발 DynamoDB 합성 시험에서 신청자와 심사자가 같은 계정인 경우 관리자 차단 중 심사 거부와 차단 해제 후 심사, 두 차례 신청 이력의 목록·잠금 기반 삭제를 확인했다. 이 시험에는 전용 티어 GSI가 없는 기존 개발 테이블을 사용했다.
개발 DynamoDB 합성 시험에서 일부 티어 이력을 삭제한 다음 잠금을 다른 요청으로 교체하거나 해제하면 기존 요청의 후속 삭제가 거부되고 나머지가 유지되는 것을 확인했다. 원래 잠금을 복원하면 재개할 수 있다.

티어 삭제 작업자는 신뢰된 호출자가 주입한 진행 저장기와 암호화기를 사용해 삭제 잠금 아래 첫 페이지부터 반복한다. 페이지 처리 뒤에만 진행 버전을 저장하므로 충돌·응답 유실 후 남은 첫 페이지를 재처리할 수 있다. 빈 페이지는 `VERIFYING` 관찰일 뿐 GSI·백업·다른 저장소 삭제나 전체 완료를 의미하지 않는다. 진행 저장기·암호화기는 별도 초안 PR에 있으며 인증된 실행 서비스·배포는 아직 연결되지 않았다.

티어 신청의 `PendingRequests` 인덱스 정렬 키는 `submitted_at#application_id`다. 티어 삭제 작업자는 신청 이력에서 해당 키 후보를 페이지별로 수집해 암호화된 진행 기록에 보존하고 수집이 완료되어야 삭제를 시작한다. 후보는 제한된 크기의 암호화 페이지로 분할하고 페이지 저장 후 진행 위치를 갱신한다. 실제 삭제 서비스에 연결하기 전에 인덱스 지연 반영 검증 절차가 필요하다. 인덱스에서 한 번 보이지 않는 것은 비동기 반영 완료의 증거가 아니다.

`deletion_index_candidates`는 같은 삭제 요청의 잠금을 확인한 뒤 고객의 신청 원본을 강한 일관성으로 페이지 조회해 `PendingRequests` 정렬 키 후보를 도출한다. 반환값과 커서에는 고객 정보가 포함될 수 있어 신뢰된 작업자만 취급해야 한다. 잠금은 조회 이후에도 유지된다는 보장이 없고 후보의 암호화 저장과 삭제 전 수집 확인을 연결했으나 GSI의 실제 반영 확인은 남았다. 각 암호화 페이지는 최대 20건이며 진행 위치와 페이지를 재조회해 누락 여부를 확인한다.

보존된 티어 인덱스 후보는 잠금 확인 후 `PendingRequests`에서 정확한 정렬 키로 관찰한다. 충돌 행을 페이지별로 확인하며 `PRESENT`, `NOT_OBSERVED`, `INCONCLUSIVE`를 구분하고 후보 평문은 결과에 포함하지 않는다. GSI는 최종 일관성이므로 `NOT_OBSERVED`는 조회 시점의 관찰일 뿐 삭제 완료나 반영 완료를 증명하지 않는다. 전용 개발 티어 테이블·GSI와 실행 역할에서의 검증은 남아 있다.

티어 인덱스 후보별 최신 관찰 상태와 시각은 같은 삭제 잠금 및 예상 버전 아래 암호화된 진행 기록으로 저장할 수 있다. 재관찰은 새 버전으로 갱신하며, 이는 관찰 기록이지 GSI 반영 보장이나 삭제 완료 증거가 아니다. 전용 GSI에서의 검증과 전체 작업자 연결은 남았다.

`FOODTECH_TIER_GSI_LIVE=1`과 `AWS_PROFILE=foodtech`로 `tests/live/tier_gsi_observation_check.py`를 명시적으로 실행하면 합성 행의 인덱스 출현과 삭제 뒤 미관찰을 확인한다. 일회성 `foodtech-tier-gsi-test-*` 테이블을 지정해 실제 DynamoDB GSI에서 출현·삭제 뒤 미관찰을 확인하고 합성 기록과 테이블을 정리했다. GSI 미관찰은 해당 시점의 관찰일 뿐 삭제 완료 증거가 아니다. 실제 티어 테이블·배포 역할 및 작성자 중지 증명은 이 시험에 포함되지 않는다.

새 배치 변경은 대기 항목에 16개 샤드 중 하나를 기록한다. CDK는 대기 항목만 표시되는 `MealAggregatePending` sparse GSI를 정의하며 `process_pending_page`는 샤드별 페이지를 조회해 각 항목을 처리하고 실패 수와 다음 커서를 반환한다. GSI는 결과 반영이 지연될 수 있으므로 호출자는 전 샤드의 모든 페이지를 반복 순회해야 하며, 실패한 항목은 남아 다음 순회에서 다시 시도된다. 인덱스 생성 이전에 저장된 대기 항목은 샤드 속성이 없어 발견되지 않으므로 배포 전 별도의 안전한 백필과 검증이 필요하다. 이 코드는 인덱스 배포나 주기 실행을 설정하지 않는다.

`python -m foodtech_business_api.combi_refresh_worker`는 `FOODTECH_COOKING_TABLE`과 `FOODTECH_AUTH_TABLE`이 명시된 경우 16개 샤드의 모든 페이지를 한 차례 순회한다. 각 실패는 합계에 포함하고 대기 항목을 남기며 실패가 하나라도 있으면 비정상 종료한다. 반복 커서와 샤드당 페이지 한도 초과도 실패다. 정기 실행·경보·실행 역할 연결은 별도다. `combi_refresh_backfill.backfill_pending_page`는 이전 대기 항목을 페이지 단위로 스캔하고 같은 버전·대기 상태·샤드 속성 부재를 조건으로 인덱스 속성만 추가한다. 누락 없이 전환하려면 이전 버전의 모든 작성자를 중단한 뒤 전체 페이지를 반복 확인하고, 스캔 비용과 실행 권한을 검토해야 한다. 실행 명령이나 자동 배포에는 연결하지 않았다.

개발 DynamoDB의 단일 합성 대기 항목으로 오래된 버전의 백필 거부, 현재 버전 백필과 시험 항목 정리를 확인했다. 실제 테이블의 전체 스캔이나 백필은 수행하지 않았다.

`infra/containers/combi-refresh-worker.Dockerfile`은 잠금 파일의 업무 API 의존성을 설치하고 비루트 사용자로 한 차례 순회 명령을 실행한다. CI에서 이미지 빌드와 환경변수 누락 시 실행 거부를 검사한다. 이미지 배포, 실행 역할과 스케줄은 별도 구성이며 이 Dockerfile만으로 주기 실행되지는 않는다.

개발 DynamoDB의 합성 계정에서 작업자의 계정 조회 직후 삭제 잠금이 걸리면 집계 저장이 거부되고, 결과 저장 후 잠금이 걸리면 대기 완료가 거부되는 경합을 확인했다. 두 경우 대기 항목을 보존하며, 잠금을 해제한 시험 계정에서 재시도한 후 시험 항목을 정리했다. 이는 전체 삭제 조정기의 작성자 중지 증명을 대체하지 않는다.

`provisionMealRefreshSchedule=true` CDK 초안은 기존 역할·프라이빗 네트워크·이미지 digest·전달 실패 DLQ·실측할 주기를 파라미터로 받아 비활성 EventBridge 규칙과 비루트 Fargate 작업을 합성한다. 역할 정책과 신뢰 관계, 서브넷의 ECR·로그·DynamoDB 접근, DLQ 정책, 동시 작업 제한과 계정 삭제 시 작성자 중지 증명은 별도로 검증해야 한다. EventBridge DLQ는 작업 실행 요청 전달 실패용이며 컨테이너의 비정상 종료나 내부 실패를 보장해서 포착하지 않는다. 작업 종료 경보의 실제 전달·알림과 재시도를 확인하고 기존 대기 항목을 백필하기 전에는 규칙을 활성화하지 않는다. 이 스택은 아직 배포하지 않았다.

작업 스케줄 초안은 실행 요청 전달 실패 DLQ와 별도로 지정된 ECS 작업 그룹의 STOPPED 이벤트를 보관한다. 종료 코드가 0이 아니거나 없으면 로그 지표와 CloudWatch 경보 상태를 만든다. 이 경보에는 알림 대상이나 자동 재시도가 연결되지 않으며, 이벤트·로그 전달 실패 또는 작업이 실행되지 않은 상황까지 감지한다는 뜻이 아니다. AWS의 `TestMetricFilter`로 0 종료 제외와 비정상·누락 종료 포함을 확인했으며 실제 리소스는 배포하지 않았다.

로컬 통합 시험은 같은 샤드의 여러 대기 항목을 한 페이지씩 순회하면서 첫 집계 저장의 일시 실패, 다음 항목의 정상 처리, 다음 순회의 재시도와 빈 재순회를 확인한다. 인덱스 조회는 메모리 대체 구현이므로 배포된 DynamoDB GSI의 전파 지연과 실행 역할 검증은 포함하지 않는다.

`backfill_pass`는 페이지별 조건부 백필을 한 번 끝까지 수행한다. 갱신이나 경합이 있었다면 `RESCAN`을 반환하고, 둘 다 관찰되지 않은 전체 순회는 `OBSERVED_CLEAN`으로 표시한다. 커서 반복·페이지 상한 초과는 오류다. `OBSERVED_CLEAN`은 해당 순회의 관찰일 뿐 이전 작성자 중지나 테이블 전체의 동시점 스냅샷을 증명하지 않으며, 실제 호출 경로는 아직 연결하지 않았다.

일회성 On-Demand 테스트 테이블에 같은 GSI를 만들어 실제 인덱스 전파, 페이지 조회를 통한 작업자 대기 완료, 삭제된 대기 항목의 인덱스 제거를 확인했다. 별도 합성 계정과 항목 및 테스트 테이블을 삭제했다. `tests/live/combi_refresh_index_dynamodb_check.py`는 별도로 생성한 `foodtech-refresh-test-*` 테이블과 명시적 opt-in이 필요하며, 테스트 테이블 생성·삭제는 담당하지 않는다. 이 실험은 배포 역할이나 실제 업무 GSI를 검증하지 않는다.

동일한 일회성 GSI 시험을 집계 그룹이 연결된 합성 배치로 확장했다. 배치 버전 1의 이력 스냅샷을 만든 뒤 버전 2 변경을 인덱스에서 발견·재집계하고, 새 결과의 참조 버전 2와 기존 결과의 참조 버전 1을 확인했다. 품질평가가 없는 제외 표본 사례이며 실제 평가·배포 역할·업무 GSI 검증은 별도다. 합성 항목과 테스트 테이블을 삭제했다.

일회성 GSI 시험을 유효한 합성 고등어 품질평가가 포함된 표본으로도 실행했다. 인덱스 발견 이후 버전 2로 다시 집계해 표본 수 1과 평균 80.00을 유지하고 버전 1 스냅샷을 보존함을 확인했다. 합성 항목과 테스트 테이블은 삭제했다. 개인 AWS 개발자 자격증명으로 수행한 시험이며 배포된 역할 검증은 아니다.

대량 재집계의 진행 위치와 완료는 계정 상태·epoch·배치 버전·이전 위치를 같은 트랜잭션으로 확인한다. 배치가 다시 변경되면 기존 진행 위치를 버리고 새 버전부터 다시 시작한다. 로컬 1,001개 연결 시험과 개발 DynamoDB의 합성 진행 위치 저장·오래된 위치의 저장 및 완료 거부를 확인했다. 실제 1,001개 DynamoDB 그룹 처리량과 배포된 역할 검증은 아직 없다.

작업자의 순회 결과에는 `processed`와 별도로 `partial`을 출력한다. `partial`은 이번 구간을 처리했지만 대기 항목이 남은 건수이며 성공적으로 전체 완료했다는 뜻이 아니다. 예상하지 못한 처리 상태는 실패 건수에 포함해 다음 순회에서 재시도하도록 한다.

작업자 IAM 후보를 AWS IAM Policy Autopilot으로 추출할 때 트랜잭션의 실제 항목별 동작을 구분하지 못해 불필요한 동작이 포함되었다. CDK에서 확인한 두 개발 테이블 이름을 분석 전용 입력으로 제공한 후 IAM 정책 시뮬레이터를 리소스별로 실행한 결과, 다른 테이블은 거부됐지만 인증 세션 테이블의 `DeleteItem`이 허용됐다. 이 후보는 사용하지 않는다. 실제 역할에는 인증 테이블 읽기·조건 확인과 업무 테이블/인덱스의 필요한 동작을 분리하고, 허용·거부 양방향 및 트랜잭션을 실제 역할로 검증해야 한다. 이 검토는 역할 생성이나 정책 적용을 수행하지 않았다.

## 원천 읽기 broker의 내부 권한 계약

`recipe_read_broker`는 인증된 고객 세션·실행·현재/직전 작업을 다시 확인하고, 별도 `source_read_authority`가 승인한 두 원천에 대해서만 STS 읽기 세션을 발급하는 내부 구성요소다. 작업의 배치 연결이나 고객 입력은 원천 읽기 권한을 만들지 않는다. 발급 전후에 계정 epoch·탈퇴 잠금·권한 기록을 재확인하며, 임시 자격증명은 일반 JSON·pickle·repr에 노출하지 않는다. 명시적인 Fargate 역할 확인과 활성화 설정 없이는 기본 실행하지 않는다.

`gateway_recipe_scope.issue_customer_recipe_reads`는 고객 세션·CSRF 확인 후 기존 loopback mTLS 설정으로 Gateway의 `POST /internal/ai/recipe-scopes/{execution_id}`를 조회한다. Gateway가 강한 조회로 얻은 동일 실행의 소유자·기능·작업/원천 버전·상태만 반환하며 `Cache-Control: no-store`를 지정한다. 프롬프트·credential·모델 응답은 제외한다. 수신자는 다른 소유자, 종료된 실행, 누락/추가 필드, 중복 JSON 멤버, 4KB 초과 응답과 redirect를 거부한다. 이 관찰을 발급 전후의 세션·실행 재검사에 사용하며, 실행 레지스트리의 직접 읽기 권한을 Business API에 추가하지 않는다. 고객 cookie를 내부 요청으로 전달하지 않는다. 이 함수는 HTTP 응답을 만들지 않으며 lease를 브라우저로 내보내지 않는다.

인증 도메인의 USER는 opaque grant ID를 참조하고, 별도 source-access catalog는 원천·권한 종류·상태·버전·명시 만료만 보관한다. catalog에 원문 고객 주체를 복제하지 않는다. `source_read_registrar`는 별도로 인가된 등록자에게 주입된 클라이언트만 사용하는 내부 처리다. 계정 epoch·중단·탈퇴 잠금·기존 grant map을 조건 검사하면서 USER 참조와 catalog 레코드를 한 트랜잭션으로 등록하거나 회수한다. 기존 권한의 묵시적 덮어쓰기나 경쟁 실패 후 무조건 갱신은 하지 않는다. 등록 만료는 호출자가 반드시 지정하며 TTL 정리를 기다리지 않고 읽기 시점에 만료를 검사한다.

실제 authority 조회는 두 grant의 ID·버전·만료와 인증 epoch를 `SourceReadAuthorization`으로 보존한다. 발급 전후 관찰이 달라지면 lease를 폐기하고, 일치한 관찰만 private lease에 결합한다. 이 관찰은 자격증명이나 인가 서명이 아니며 별도의 현재 권한 검사를 생략하는 근거가 아니다.

`recipe_read_delivery`는 검증된 관찰과 explicit 임시 키가 있는 lease만 전용 mTLS 요청 본문으로 인코딩한다. 일반 JSON 변환·repr·pickle에는 키를 내보내지 않는다. 요청 목적지는 기존 loopback Gateway 설정과 고정 실행 URI로 제한하고 cookie·proxy 환경·redirect·자동 재시도를 사용하지 않는다. 키는 URL·헤더·고객 응답에 포함하지 않는다. 응답은 같은 실행의 네 필드(`execution_id/state/response_text/error_code`)만 허용하고, 오류 본문이나 예상하지 않은 필드는 일반화된 실패로 처리한다. 전송용 요청 바이트와 SDK의 메모리 복사본 전체가 영구적으로 소거된다고 주장하지 않는다.

전송 함수와 Gateway 수신 함수를 실제 로컬 mTLS 시험 서버로 연결한 시험은 통과했다. 이 서버는 합성 키·모의 STS/DynamoDB와 명시적인 권고 차단 응답만 사용한다. production의 `/internal/ai/recipe-executions/{execution_id}/invoke`는 아직 등록하지 않았으며, 고객 화면에서 이 전송 함수를 호출하지 않는다. 실제 AWS 범위 검증과 authoritative 근거가 연결되기 전에는 실행을 활성화하지 않는다.

기존 근거 조회의 제육볶음 투입 시간 계산은 공통 `jeyuk_feed_timing` 계약을 사용한다. Gateway의 관측 입력 추출도 같은 고기 투입 완료 기준·투입 그룹·30초 동시성 계산을 사용하며, 고객 API의 시간 계산이나 권고 가능 상태를 바꾸지 않는다.

`GET /api/customer/ai/recipe-executions/{execution_id}/status?job_id=...`는 현재 고객이 소유한 작업과 연결된 권고 실행 상태만 조회한다. 내부 mTLS POST에는 서버가 결정한 tenant를 본문에 담고, 실행·작업 연결 및 안정된 상태/결과 기록을 대조한다. 응답은 상태·요청 당시 작업 버전·결과 기록 유무만 포함하며 원문 응답·키·오류 상세는 반환하지 않는다. 조회 후 세션과 작업을 다시 확인하고, 작업 버전이 달라졌으면 `job_changed`로 표시한다. 이 API와 기존 일반 실행 상태 조회에는 `Cache-Control: no-store`를 지정한다.

고객 화면은 전환 확인 전에 고지의 child execution ID를 보관한다. 응답이 유실돼도 같은 ID로 상태만 조회하고 새 확인 POST/AI 호출을 자동 실행하지 않는다. 같은 전환 실행 기록을 찾으면 확인된 상태로 표시하며, 잘못된 UUID는 전송하지 않는다. 알려진 ID의 조회 복구이며 실행 ID를 받지 못한 최초 요청을 자동 발견하거나, 원문 권고의 조회·승인을 구현한 것은 아니다.

현재는 모의 SDK 시험을 통과한 구현 후보다. 등록자 API·실행 역할, 고객 요청→Gateway의 credential 전달, 고객 실행 경로에서의 모델 전후 재인가·원자적 정산 연결, catalog의 계정 삭제·복원 체크포인트 및 실제 AWS 허용/거부 검증은 후속 작업이다. 기존 권고 차단을 해제하거나 고객에게 credential 응답을 추가하지 않는다. 읽기 권한은 독점 삭제 소유권이 아니며, STS 세션 발급 뒤 권한을 회수해도 발급된 AWS 자격증명이 즉시 폐기되는 것은 아니다. 두 opt-in CDK 후보는 기본 배포에서 제외된다.

## 일반 탈퇴의 7일 취소 유예 내부 전이

2026-11-22 승인한 일반 탈퇴 정책의 내부 상태 전이를 `account_withdrawal.py`에 추가했다. 서버 요청 시각부터 168시간 미만에는 취소할 수 있고, 경계 시각부터는 `DELETING`으로 전환한다. 요청과 취소·만료는 인증 상태 항목의 epoch와 기존 탈퇴 필드를 조건부로 대조하며, 없는 계정을 만들지 않는다. 요청 즉시 `suspended`와 epoch 증가로 기존 서비스 세션·보호된 쓰기를 차단한다. 취소는 다른 관리자 정지가 추가되지 않았을 때만 허용하고 기존 관리자 권한 제한은 유지한다. 중복 요청은 취소 기한을 연장하지 않는다.

삭제 등록은 탈퇴 상태가 있는 계정에 대해 일치하는 요청의 `DELETING` 상태만 받아들인다. 유예 중이거나 취소된 일반 탈퇴 요청은 파괴적 삭제 등록으로 진행하지 않는다. 탈퇴 상태가 없는 기존 내부 삭제 계약은 별도로 남아 있으며, 호출자 인증과 적법한 별도 삭제 요청 구분은 상위 경계에서 필요하다.

`tests/live/account_withdrawal_dynamodb_check.py`로 기존 개발 인증 테이블의 합성 계정 두 건에서 요청·취소·만료, 168시간 경계, 오래된 읽기 이후 epoch 경합 거부와 별도 계정 보존을 확인하고 모든 시험 항목의 삭제·부재를 확인했다. 논리 서버 시각을 주입한 시험이며 실제 7일 경과·고객 본인 인증·Cognito 삭제/동일 이메일 재가입·백업 복원·배포 역할은 검증하지 않았다. 내부 전이만으로 신규 계정 초기화, 공개 탈퇴 API·고객 화면, 삭제 작업자와 전체 삭제 완료가 구현됐다고 판단하지 않는다.

탈퇴 요청·취소 API와 고객 화면은 `FOODTECH_ACCOUNT_WITHDRAWAL_ENABLED=true`에서만 제공한다. 기본값은 비활성이며 계정 초기화·Cognito 수명주기·삭제 작업자·실제 역할 검증 전에는 배포 활성화하지 않는다. 요청은 고객 세션·CSRF·명시적 확인과 같은 계정 epoch를 요구한다. 취소 로그인은 기존 고객 callback의 서버 보관 purpose와 PKCE state에 결합하고 `prompt=login`, `max_age=0`을 요청한다. callback은 서명 검증된 ID 토큰의 `auth_time`이 해당 흐름 시작 이후인지 확인한다. 공급자가 새 인증을 확인해 주지 않으면 취소 세션을 발급하지 않는다. [Cognito 재인증 매개변수](https://docs.aws.amazon.com/cognito/latest/developerguide/authorization-endpoint.html)를 참고한다.

취소 전용 서버 세션은 최대 5분이고 일반 고객·관리자 세션으로 사용할 수 없다. 취소는 해당 세션의 CSRF와 현재 계정 상태를 다시 확인하며 성공 후 세션을 제거하고 일반 로그인을 요구한다. 모의 Cognito 응답·메모리 공유 저장소를 사용하는 API 시험에서 기존 세션 차단, 취소 전용 범위, 오래된 인증·다른 계정·기한 만료·관리자 정지 거부와 CSRF를 확인했다. 실제 Cognito 재인증·이메일 해제·재가입 및 배포 환경의 권한 검증은 아직 수행하지 않았다.

`tests/live/withdrawal_browser_harness.py`는 실제 업무 API와 빌드된 고객 UI를 로컬 루프백에서 띄우며, Cognito·계정 저장을 명시적인 합성 대체 객체로 실행한다. 외부 공급자·AWS 호출은 수행하지 않는다. 합성 본인 인증 화면을 거쳐 탈퇴 요청 → 일반 서비스 화면 제거 → 취소 전용 화면 → 취소 후 재로그인 안내를 브라우저에서 확인했다. 대기·취소 화면에 일반 가입 안내가 중복 표시되는 문제도 수정했다. 이 결과는 실제 Cognito 본인 인증이나 공개 배포 검증이 아니다.

기한이 지난 일반 탈퇴는 요청 ID를 명시해 `IdentityVault.resolve_deletion`에서 `DELETING`·정지 상태, 요청 시각·168시간 기한과 계정 epoch를 대조한 스냅샷만 해결한다. `GuardedDeletion.lock_and_register`는 같은 요청·시각·기한·epoch·Vault/Capsule revision을 네 저장소 트랜잭션에서 다시 검사한다. 기존 활성 계정용 내부 삭제는 탈퇴 상태가 있는 계정에 적용되지 않는다. 유예·취소 상태를 활성 계정으로 간주해 우회하지 않는다.

`tests/live/withdrawal_lock_dynamodb_check.py`로 기존 네 개발 테이블과 KMS에서 합성 계정의 유예 중 거부, 조회 후 기한 변경 시 전체 트랜잭션 거부, 만료 후 계정·Vault·Capsule 잠금과 암호화된 삭제 기록의 동시 생성을 확인했다. 모든 생성 항목을 삭제하고 부재를 확인했다. 요청 시각을 과거로 이동시킨 합성 시험이며 실제 가입·Cognito 삭제·이메일 재사용·업무 자료 전체 삭제·복원·배포 역할은 검증하지 않는다. 만료 작업자의 예약 배포와 계정 초기화·최종 제거 경계의 운영 적용은 후속 작업이다.

`WithdrawalDispatcher`는 전용 내부 작업자용 페이지 탐색과 단건 만료 전달을 제공한다. `PENDING` 및 아직 잠기지 않은 `DELETING` 후보를 조회한 뒤 계정 상태를 다시 읽고, 조건부 만료 → Vault/Capsule 해결 → 암호화 → 네 저장소 잠금으로 처리한다. 빈 Scan 페이지의 후속 커서를 보존하며, 인증 테이블 커서에는 세션 키가 포함될 수 있어 repr에서 숨기고 신뢰된 프로세스 메모리에서만 전달한다. 커서를 로그·HTTP·평문 파일에 출력하지 않는다. 재시작 시 처음부터 재탐색하며 Scan 종료를 전체 삭제 완료로 간주하지 않는다.

각 암호화 준비 시도는 별도 트랜잭션 시도 ID를 사용하고, 동일 삭제 요청의 잠금·Registry 조건은 계속 검사한다. 응답이 불확실하거나 이미 잠긴 경우에는 복구 확인을 요구하며 새 잠금이나 완료 receipt를 발급하지 않는다. 작업자 시험 6건은 페이지 경계·취소·기한·오류·재시도·민감 커서 출력을 확인했고, 개발 DynamoDB·KMS에서 특정 합성 계정의 실제 단건 dispatch와 재잠금 방지를 확인했다. 실제 인증 테이블 전역 Scan은 수행하지 않았다. 별도 실행 역할·스케줄·현재 Registry를 소비하는 전체 삭제 작업자 연결과 배포는 아직 남아 있으며 웹 API 역할에 Scan 권한을 추가하지 않았다.

## 계정 초기화와 최종 제거의 동시성 경계

`FOODTECH_PRINCIPAL_PROVISIONING_ENABLED=true`이면 고객·관리자 로그인에서 존재하지 않는 인증 상태를 초기화할 수 있다. `CONTROL#PRINCIPAL_ENROLLMENT`의 현재 세대를 먼저 읽고 현재 Cognito의 활성·확정 계정과 정확한 `sub`를 다시 확인한 뒤, 같은 세대와 계정 부재를 조건으로 초기 상태를 저장한다. 기존 정지·삭제 잠금은 덮어쓰지 않는다. 이 모드에서 기존 세션의 인증 상태가 사라졌으면 세션을 거부하고 자동으로 재생성하지 않는다.

`DynamoPrincipalRetirement`는 Cognito에서 해당 이전 주체가 실제로 부재하며 Registry가 같은 요청의 `COMPLETED`인 경우에만 계정 상태 제거와 제어 세대 증가를 한 트랜잭션으로 수행한다. 이전 계정을 지우기 전에 읽은 세대로 초기화하려는 요청은 실패한다. Cognito 삭제 자체, 삭제 완료 상태의 정당성, 작성자 중지·저장소 잔존·백업 검증은 상위의 신뢰된 삭제 작업자가 보장해야 하며 이 구성요소는 이를 대신하지 않는다. 이메일별 장기 식별자나 영구 재가입 차단 목록을 추가하지 않는다.

제어 항목은 개인정보가 없는 별도 운영 기록이며 TTL을 두지 않는다. 초기 구성 시에만 신뢰된 유지관리 경계에서 명시적으로 준비하고 로그인·앱 시작 중 자동 생성하지 않는다. 기존 세대를 0으로 재설정하거나 과거 백업으로 되돌리면 오래된 초기화 요청을 막지 못하므로 현재 제어 기록을 보존해야 한다. 모든 계정 최종 제거 경로가 같은 제어 기록을 사용해야 하며, 일반 API 역할의 직접 `USER#` 삭제·제어 기록 변경을 허용하지 않는 권한 경계와 배포 검증이 필요하다. 현재 해당 권한·배포 적용은 미완료이므로 기본 비활성을 유지한다. 신규 탈퇴 요청은 두 기능 플래그와 준비된 제어 항목을 요구한다.

`tests/live/principal_enrollment_dynamodb_check.py`는 실제 운영 제어 항목 대신 별도 합성 키를 사용한다. 개발 DynamoDB에서 초기화, 완료 전 최종 제거 거부, 완료를 모사한 기록 아래 제어 세대 증가와 이전 계정 제거의 원자성, 오래된 초기화 거부, 새 주체의 초기화 및 실제 조리 저장소의 보호된 쓰기를 확인했다. Cognito는 임의 시험 주체의 부재만 조회했으며 사용자 생성·수정·삭제나 이메일 재가입을 수행하지 않았다. 합성 제어·계정·Registry·업무 시험 항목은 삭제하고 부재를 확인했다. 실제 고객 가입·재가입, 전체 삭제 완료와 배포 역할 검증은 별도다.

## 만료된 Cognito 주체 제거 경계

`CognitoWithdrawalRelease`는 전용 내부 작업자가 준비된 초기화 제어 항목과 계정·Registry의 일치하는 삭제 잠금, 만료된 요청·기한·epoch를 확인한 경우에만 이전 Cognito 주체를 제거한다. Cognito가 반환한 재사용 가능한 Username이나 이메일을 삭제 대상에 사용하지 않고, 서버에서 확인한 이전 `sub`를 그대로 사용한다. 호출 직전 삭제 권한 상태를 다시 읽고, 호출 후 해당 주체의 부재가 확인되어야 계정 상태에 신원 제거 기록을 조건부 저장한다. 인증 상태와 삭제 잠금은 전체 데이터 삭제·최종 제거가 끝날 때까지 남긴다. 반환 상태는 신원 제거 단계이며 전체 삭제 완료가 아니다. 모호한 응답은 새 상태 조회와 재처리로 확인하고 다른 주체나 새 요청을 삭제하지 않는다. [AdminDeleteUser 식별자 계약](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminDeleteUser.html)을 따른다.

Cognito의 `sub`는 [AWS 문서](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html)에 따라 UUID 모양을 소유권이나 유효성의 근거로 삼지 않는다. 인증 주체는 기존 프로젝트 키 경계인 1~128자의 영문·숫자·하이픈·밑줄 안에서 원래 값을 그대로 보존한다. 이메일·키 구분자·공백은 거부하고 임의의 정규화·대소문자 변경·절단을 하지 않는다. 요청·작업·내부 Vault 식별자의 UUID 규칙은 유지한다. 계정 초기화·탈퇴·Vault·삭제 발견/진행·복구에서 같은 주체 검증을 사용한다.

업무 API 전체 시험 552개가 통과했다. 대체 Cognito 시험에서는 정확한 이전 주체만 제거하는 계약과 응답 유실·권한 변경을 확인했다. `tests/live/withdrawal_lock_dynamodb_check.py --identity-release-env <로컬 업무 설정 파일>`의 별도 검증은 실제 Cognito 삭제 호출을 금지한 대체 진입점으로 실행해 임의 주체의 부재 조회·조건부 제거 기록만 확인하고 생성된 합성 항목을 정리한다. 실제 일회용 주체의 제거·이메일 재사용은 아래의 전용 시험으로 검증했다. 별도 실행 역할과 예약 실행·전체 삭제 조정기에 연결하기 전에는 활성화하지 않는다.

신원 제거 전용 작업자는 `CognitoWithdrawalRelease.scan_page`로 만료·잠긴 요청을 한 페이지씩 찾고 각 후보를 같은 `release` 경계에서 다시 인가한다. 페이지 제한은 최대 100개의 평가 항목이며 빈 페이지의 후속 커서를 유지한다. 인증 테이블의 커서에는 세션 키가 들어갈 수 있어 repr에서 숨기고 신뢰된 작업자 메모리에서만 사용한다. 삭제·기록 응답이 불확실하면 복구 확인 대상으로 남기며 이전 sub의 부재를 다시 확인해 재시도한다. 페이지 종료는 전체 삭제 완료가 아니다. 이 작업자는 Vault/Capsule 복호화나 Registry 완료 권한을 필요로 하지 않는다. 페이지 처리·오래된 후보·삭제 후 응답 유실·빈 페이지·커서 검증을 대체 저장소로 확인했으며 실제 인증 테이블 전역 Scan·예약 실행·역할 배포는 수행하지 않았다.

신원 제거 명령은 ECS Fargate에서만 실행한다. 같은 stage의 `foodtech-withdrawal-identity-task-<stage>` 역할 ARN을 `FOODTECH_WITHDRAWAL_IDENTITY_TASK_ROLE_ARN`으로 명시하고, 실제 SDK provider가 container-role이며 STS의 계정·assumed-role ARN이 이 값과 일치해야 업무 클라이언트를 생성한다. 로컬 login·정적 환경 키·일반 AssumeRole은 이 명령에서 대체 사용하지 않는다. 동일 Session/timeout 설정을 STS·DynamoDB·Cognito에 전달하고 사용자 지정 AWS endpoint 설정을 무시한다. `FOODTECH_WITHDRAWAL_IDENTITY_MAX_SECONDS`는 10~600초(기본 600초)로 자격증명 획득·초기화·전체 페이지 처리를 함께 제한한다. 시간 초과·SDK 실패는 민감 응답 없이 실패하며 정상 종료해도 신원 제거 단계만 의미한다. 배포된 Task의 역할 인수·실제 Cognito 호출·전체 삭제 검증은 별도로 수행해야 한다.

전용 실행 명령은 `python -m foodtech_business_api.withdrawal_identity_worker`다. 별도 역할에서 `FOODTECH_WITHDRAWAL_IDENTITY_WORKER_ENABLED=true`, 같은 stage의 `FOODTECH_AUTH_TABLE=foodtech-auth-sessions-<stage>`·`FOODTECH_DELETION_REGISTRY_TABLE=foodtech-deletion-registry-<stage>`, `FOODTECH_COGNITO_USER_POOL_ID=ap-southeast-2_<pool>`를 명시해야 한다. 기본적으로 비활성이고 설정 오류는 AWS 클라이언트 생성 전에 종료 코드 2로 거부한다. 실행은 현재의 초기화 제어 항목을 읽기만 하며 자동 준비·세대 초기화를 하지 않는다. 실행 역할의 단기 자격증명을 사용하고 특정 개발 프로파일이나 고객·API 자격증명을 내장하지 않는다.

한 번의 순회는 `FOODTECH_WITHDRAWAL_IDENTITY_PAGE_SIZE`(기본 20, 최대 100)와 `FOODTECH_WITHDRAWAL_IDENTITY_MAX_PAGES`(기본 1000, 최대 10000)로 제한한다. 빈 중간 페이지도 계속 처리하고 커서 반복·한도 초과·조회 실패는 비정상 종료한다. 후보의 차단·불확실한 결과를 합산해 하나라도 있으면 종료 코드 1을 반환한다. 출력에는 건수와 순회 종료 여부만 포함하고 주체·요청·커서를 넣지 않는다. `scan_finished=true`나 정상 종료는 신원 제거의 해당 순회 결과이며 전체 삭제 완료가 아니다. 결과의 `deletion_complete`는 항상 false다. 중단 뒤에는 새 순회로 현재 잠금·부재를 다시 확인한다.

기존 `combi-refresh-worker` 빌드 산출물에는 같은 업무 패키지가 포함되므로 별도 Task의 명령을 `python -m foodtech_business_api.withdrawal_identity_worker`로 지정해 사용할 수 있다. 명령·역할·예약 작업은 재집계 작업과 분리해야 한다. CI는 이 이미지에서 새 모듈 로드와 설정 없는 실행의 거부를 검사한다. 이 변경은 이미지를 배포하거나 작업을 실행하지 않는다. 로컬에서는 Docker가 없어 이미지 검증을 CI에 맡기며, 실제 Cognito 시험은 앞서 기재한 일회용 계정의 단건 경계에 한정한다.

### 동일 이메일의 새 주체 분리 실검증

2026-11-22 `tests/live/withdrawal_cognito_rejoin_check.py --business-env <로컬 업무 설정 파일> --allow-disposable-cognito-users`를 기존 개발 Cognito·DynamoDB·KMS에서 실행했다. 이 실행의 고유한 `example.invalid` 이메일만 사용했고 `MessageAction=SUPPRESS`, `ForceAliasCreation=False`로 발송과 다른 계정의 별칭 이전을 금지했다. 비밀번호는 실행 메모리에서만 생성했으며 실제 고객 계정과 Pool·App Client 설정은 변경하지 않았다. Lambda trigger가 있는 Pool은 시험을 거부한다. 계정 확정은 명시적인 관리자 합성 fixture 설정이며 고객의 이메일 소유 확인을 증명하지 않는다. [AWS의 발송 억제·별칭 정책](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AdminCreateUser.html)을 따른다.

합성 요청 시각을 168시간 이상 과거로 이동한 뒤 실제 만료 dispatch·네 저장소 잠금 → 이전 sub의 Cognito 제거·부재 확인 → 같은 이메일 및 생성 Username으로 새 계정 생성 → 새 sub의 초기 상태 생성을 확인했다. 이전 삭제를 다시 실행해도 새 Cognito 주체가 유지됐고 이전 인증 상태·삭제 잠금·Registry의 `DELETING`은 보존됐다. 새 계정에는 이전 권한·동의·Vault 연결이 없는 초기 상태만 생성됐다. 종료 시 이 실행에서 생성한 Cognito 주체와 DynamoDB 항목을 모두 제거하고 부재를 확인했다.

이 실검증은 앞선 부재 조회 전용 시험과 별도이며, 실제 고객 가입·이메일 인증·OAuth 재인증·7일 실시간 경과·전체 업무 자료 삭제·백업 잔존 상한·배포 실행 역할을 검증하지 않는다. 예약 작업자와 전체 삭제 조정기에 자동 연결하지 않았고 기능 플래그는 계속 기본 비활성이다. Registry를 완료로 만들거나 작성자 중지 검사를 우회하지 않았다.
## 초기화된 계정과 티어의 삭제 보호

`FOODTECH_PRINCIPAL_PROVISIONING_ENABLED=true`일 때 DynamoDB 티어 신청·심사의 계정 조건도 초기화 모드에 맞춰 상태 항목의 존재를 요구한다. 신청자·심사자는 정확한 세션 epoch를 대조하고, 심사 대상 고객도 존재하는 정상 숫자 epoch를 요구한다. 계정 부재나 epoch 부재를 0으로 간주하지 않는다. 정지·삭제 잠금·관리자 권한 차단 검사는 그대로 적용하며 요청 조회와 변경 사이의 경쟁도 같은 저장 트랜잭션으로 거부한다. 관리자 대기 목록은 이 모드에서 부재·불일치·잘못된 epoch의 계정을 표시하지 않는다.

이 모드는 PR #229의 계정 초기화·최종 제거 세대 계약과 함께 배포해야 한다. 기본값은 계속 false이며 여기서 계정을 임의 생성하거나 플래그를 배포 활성화하지 않는다. 비활성 상태의 이전 미초기화 계정 허용 경계를 삭제 이후의 안전 보장으로 간주하지 않는다. 초기화·최종 제거의 전체 쓰기 경계 및 역할 검증 전에는 이 플래그를 켜지 않는다. 메모리 대체 티어 저장소는 실제 DynamoDB의 원자적 계정 조건을 검증하는 경로가 아니다.

2026-11-22 이 브랜치의 업무 API 시험 403개가 통과했다. `tests/live/tier_principal_dynamodb_check.py`로 기존 개발 인증·조리 테이블의 고유 합성 계정을 사용해 상태 없는 신청자·심사자 거부, 신청 조회 직후 고객 상태가 제거된 경쟁의 원자적 거부와 초기화된 별도 계정의 신청·승인을 확인했다. 삭제된 상태 항목이나 거부된 심사 기록이 재생성되지 않았고 기존 신청은 변경되지 않았다. 모든 생성 항목을 삭제하고 부재를 확인했다. 조리 테이블은 이 실행의 임의 `TENANT#` 시험 키에만 사용했으며 실제 티어 테이블의 GSI·Cognito 가입·삭제·실행 역할과 전체 삭제 완료를 검증한 결과는 아니다.
