# Business API 인증과 첫 조리 업무 흐름

권고 근거 조회의 선택적 `comparison_id`는 같은 고객이 선택한 현재 비교를 작업·안전·평가 버전과 투입 종료 순서에 대해 다시 확인한다. 두 작업의 읽기 중 변경은 충돌로 처리한다. 선택된 이전 비교는 전체 작업 중 가장 직전이라는 뜻이 아니며, 읽기 뒤 변경 가능성이 있으므로 실제 모델 실행 시 별도 원자적 검증이 필요하다.

권고 근거는 현재 재계산에서 확인된 투입 전 마지막 표본의 온도·시각·경과시간·품질 상태만 반환한다. 표본이 오래되었는지에 대한 합격 기준은 정하지 않았으며 품질 경고도 별도로 표시한다.

완료된 합성 돈까스 작업의 고객은 `POST /api/customer/cooking-jobs/{id}/process-restatements`로 현재 작업 버전과 요청 UUID를 제출해 공정 근거 재계산을 요청할 수 있다. 요청을 조건부 저장한 후 FIFO 큐에 전달하며, 전달 실패 시 같은 UUID로 재시도한다. 상태는 같은 고객의 `GET .../process-restatements/{request_id}`에서 확인한다. 처리 전에 작업 버전이 바뀐 요청은 `STALE`로 종료하므로 최신 근거를 조회한 뒤 다시 요청한다. `FOODTECH_DATA_TABLE`, `FOODTECH_COOKING_TABLE`, `FOODTECH_ORDERED_QUEUE_URL`과 원천 버전 읽기·요청 쓰기·큐 전송 권한이 필요하다. Worker가 처리하지 못하거나 DLQ로 이동한 요청을 자동으로 복구하는 운영 절차는 후속 검증이다.

고객 권고 근거 조회는 현재 작업에 맞는 재계산 결과의 온도 표본 요약을 허용 필드만 반환한다. 오래된 재계산의 요약은 반환하지 않으며, 관찰 표본 요약은 원천 완전성이나 AI 실행 가능성 판정을 대체하지 않는다.

`FOODTECH_DATA_TABLE`이 설정되고 재계산 결과에 스트림 버전이 있으면 권고 근거 조회 전후로 연결된 원본 버전을 강한 일관성으로 읽는다. 조회 시점에 일치한 경우만 `MATCHED_AT_READ`, 바뀌었다면 `CHANGED`, 연결이 다르면 `INCONSISTENT`로 보고한다. 변경·연결 불일치에는 새 권고 요청과 전환 동의를 차단한다. 데이터 테이블 읽기 권한이 필요하며, 일치는 조회 시점과 버전 계약을 따르는 작성자에만 한정되고 AI 실행을 허용하지 않는다.

합성 조리작업의 고객 소유권과 CSRF, 조회된 작업 버전 및 일부 필수 근거를 확인한 뒤 AI 권고 요청·로컬 전환 고지·명시적 동의를 기록할 수 있다. 현재 Tier 1 모델 미설정과 전체 원천 완전성 미평가를 표시하며 이 경로는 AI를 호출하지 않는다. 조리작업 확인과 동의 저장은 별도 트랜잭션이므로 실제 실행 전에는 최신 조리작업 및 전체 근거를 다시 확인해야 한다.

밥 스팀·고등어 건열 조리의 합성 콤비오븐 공통 계산은 `foodtech_contracts.combi_cooking`에 정의한다. 승인된 메뉴별 프로그램 조리시간 경계와 인양을 포함하는 별도 열 노출시간, 밥의 건조·배수 쌀과 추가 물 기반 유효 수분량, 중형 고정 랙·대형 이동식 랙의 서로 다른 정격 하중 및 팬·랙 수 제한을 계산한다. `POST /api/customer/combi-meals`는 고객 범위의 식사 배치와 서로 다른 밥 작업·모드 전환·고등어 작업을 한 트랜잭션으로 만들며 입력 수분비와 적재 한계를 확인한다. `GET /api/customer/combi-meals/{meal_id}`는 본인의 연결 작업을 조회한다. 고객 화면에서 합성 배치 생성과 ID 조회를 제공한다. 모드 전환·고등어 투입·안전 판정은 대기 상태로 시작하며 콤비오븐 Mock과 실제 조리 흐름은 후속 연결 대상이다. 합성 규칙이며 실제 장비·식품 안전기준으로 간주하지 않는다.

`POST /api/customer/combi-meals/{meal_id}/source-observations`는 고객 배치에 C# Mock 원표본 JSONL을 한 번 연결한다. 연결 시 최신 배치 버전을 확인한다. 고객 화면에서 해당 배치와 세 작업 ID가 들어간 Mock fixture를 내려받아 실행하고 생성된 원표본을 선택할 수 있다. 서버는 세 작업의 소유 배치·합성 장비·단계 순서·1초 시각·원천 필드를 확인한 뒤 원표본을 별도 파티션의 100건 단위 항목으로 보존하고 배치 정보·이력과 한 트랜잭션에 기록한다. `GET`으로 같은 경로에 `cursor=0`부터 청크를 조회한다. 원본 바이트 확인용 SHA-256은 단순 줄바꿈 연결 해시이며 표준화 payload 해시와 별도다. 연결 자체는 조리나 공정·안전 결과를 변경하지 않는다. AWS 환경 실검증은 후속이다.

`GET /api/customer/combi-meals/{meal_id}/source-windows?phase=RICE|TRANSITION|MACKEREL&cursor=0`은 고객 소유의 전체 원표본을 다시 읽어 식별자·순번·SHA-256을 검증한 후 해당 구간의 5초 온도 요약을 25개씩 반환한다. 현재·최소·최대·평균과 목표 온도 범위 밖의 초를 표시하고 마지막 5초 미만 구간은 불완전 표본 수와 함께 표시한다. 고객 화면에서 구간과 페이지를 선택해 확인할 수 있다. 결과는 저장된 합성 원표본의 사후 조회이며 실시간 5초 전송이나 안전·공정 판정이 아니다. 조회마다 모든 원표본을 검증하므로 실제 AWS 비용·지연과 대규모 사용 적합성은 미검증이다.

`POST /api/customer/combi-meals/{meal_id}/source-assessment/{rice|transition|mackerel}`은 연결된 원표본의 해시·순서·소유 배치 및 단계 시작시각을 다시 검사한다. 밥·고등어는 조리 기간까지 일치하면 온도·습도 또는 온도·문 부분 판정을 기록한다. 전환은 명시적인 치명 알람·환기 지원·이벤트가 포함된 `synthetic-combi-v2` 표본에서만 준비 조건을 판정하며, 기존 v1 자료의 누락된 값을 추정하지 않는다. 습도는 실측 또는 미지원만 전환 기준으로 사용한다. 결과에는 원본 해시와 사용한 수신 순번 범위를 남기며 화면에서 원표본 시각을 단계 입력에 사용할 수 있다. 안전·품질·종합 판정은 별개다.

`POST /api/customer/combi-meals/{meal_id}/events`는 합성 관찰시각과 기대 버전을 받아 `RICE_STARTED → RICE_PROGRAM_COMPLETED → RICE_UNLOADED → MODE_TRANSITION_STARTED` 순서만 기록한다. 상태·해당 작업·불변 사건은 같은 트랜잭션으로 기록한다. 시간은 과거 순서대로만 입력할 수 있고 밥 프로그램 종료 시 경계별 시간 판정을, 인양 시 열 노출시간을 별도 저장한다. 시간 판정은 온도·습도 등 전체 공정 판정을 대체하지 않는다. 전환 시작은 준비 완료가 아니며 고등어 투입은 차단 상태를 유지한다. 고객 화면의 시각은 합성 수동 기록이고 장비 명령이 아니다.

`POST /api/customer/combi-meals/{meal_id}/transition-evidence`는 합성 전환 시작 이후 연속 1초 표본을 최대 300초까지 받아 온도 215~225°C, 기후 설정 10%, 문 닫힘·치명 알람 없음의 30초 연속 조건을 확인한다. 습도 지원 시 각 표본의 습도 15% 이하도 필요하고, 미지원 시 180초 경과와 지원되는 환기 플랩의 열림·닫힘 순서를 요구한다. 이전 표본과 센서 지원 여부는 변경할 수 없다. 300초 내 통과하면 `DRY_HEAT_READY`, 그렇지 않으면 `MODE_TRANSITION_TIMEOUT`으로 기록한다. 습도 미지원 상태와 근거는 별도 기록하며 실제 습도 충족으로 표현하지 않는다. 고객 화면은 지정된 정상 합성 표본을 생성해 이 경계를 시험한다. 전환 검증은 고등어의 조리·안전 판정이 아니며 실제 장비 제어를 수행하지 않는다.

전환 준비 이후 합성 고등어 작업의 투입·프로그램 완료·인양을 순서대로 기록하며 조리시간과 열 노출시간을 분리한다. 제품은 토막당 120~150g, 두께 1.5~2.0cm 범위를 적용한다. `POST /api/customer/combi-meals/{meal_id}/mackerel-safety`는 인양 즉시 시작된 서로 다른 제품·탐침의 연속 60초 표본을 확인한다. 한 랙의 세 선반 이상은 상·중·하, 두 선반은 무거운 단 두 개와 다른 단 한 개, 한 선반은 좌·중·우를 선택한다. 선반 번호는 클수록 위쪽이며 가장 두꺼운 제품 선택과 위치 증거도 해당 기준에 따라 확인한다. 한 선반의 제품이 3개 미만이면 전수 검사한다. 대형 두 랙은 각각 표본을 포함하고 더 무거운 랙에서 두 개를 선택한다. 랙 무게가 같으면 상·중·하 위치를 가능한 범위에서 최대한 포괄하고 선정 근거를 남긴다. 선정 조건이 미충족이거나 확인 불가하면 이력의 `selection_issues`에 남기고 통과시키지 않는다. 교정된 값이 하나라도 75°C 미만이면 `FAILED`, 표본 누락·교정 만료는 `ASSESSMENT_INCOMPLETE`, 모두 유효하고 75°C 이상이면 `PASSED`와 최저값을 남긴다. 이력은 새 사건으로 보존하고 실패 후 추가 가열·재검증은 별도 구간과 안전 이력으로 기록한다. 이 판정은 안전 표본에 한정된다.

`POST /api/customer/combi-meals/{meal_id}/mackerel-process`는 조리시간 전체에 해당하는 최대 900개의 1초 합성 챔버 온도·문 표본을 받는다. 최초 적재 후 문 닫힘이 2초 확인된 시점부터 120초 이내 215~225°C 30초 유지, 복원 후 200°C 미만 30초 지속, 활성 조리 중 2초 문 상태 확정 및 누적·연속 개방 경계와 시간 판정을 계산한다. 관찰·확정 초와 원표본을 보존하고 안전 결과와 별도로 부분 판정을 기록한다. 최종 표본에서 문 상태가 확정되지 않은 경우 미완료로 남긴다. 기후·팬 등 다른 공정 항목과 종합 판정은 후속 범위다.

`POST /api/customer/combi-meals/{meal_id}/rice-process`는 밥 조리 전체의 1초 합성 온도·습도·문 표본을 최대 2,000초까지 검사하고 원표본과 부분 판정을 기록한다. 저온·고온 연속 및 누적 지속시간, 습도 경고·스팀 부족 경계, 2초 문 상태 확정과 시간 판정을 적용한다. 문 표본이 전부 없는 이전 요청은 문 미측정으로 기록하며 정상으로 판정하지 않는다. 고온 급변은 센서 이상 의심으로 남기고 해당 값을 공정 타이머에서 제외하지 않는다. 습도 출처는 실측·제어기 추정·미지원으로 구분하며 미지원은 정상으로 취급하지 않는다. 팬 심각도와 종합 공정판정, 센서 이상 확정·품질 격리는 후속 범위다.

밥·고등어 공정에서 팬 단계가 일부라도 누락되거나 목표와 다르면, 이미 확인된 공정 실패가 없는 한 결과를 `INSUFFICIENT_DATA`로 둔다. 목표와 다른 값은 `FAN_DEVIATION`으로 기록하며 별도의 팬 실패 임계치를 추정하지 않는다. 밥 안전 확인에는 팬 단계 관찰이 전체 구간에서 목표와 일치해야 한다. 팬 근거가 없는 과거 밥 안전 합격과 품질평가는 이력을 유지하되 현재 조회·새 평가에서 사용하지 않는다.

`POST /api/customer/combi-meals/{meal_id}/rice-preparation`은 밥 조리 시작 전 합성 세척 횟수, 불림물 온도, 불림·배수 시각과 선택적인 세척·불림 후 중량을 기록한다. 기존 건조 쌀과 배수 후 중량은 식사 배치 생성값으로 유지한다. 시각 순서와 배수 완료 후 조리 시작을 검증하고 수정 사유와 이전 기록을 남긴다. 선택 중량을 생략하면 기존 값을 유지하고 `null`은 해당 값을 지운다. 합성 기준은 세척 3회·약 20°C·불림 30분·배수 5분이지만 기록만으로 적합성이나 안전을 판정하지 않는다.

## 구현 경계

- 로그인 흐름과 세션은 DynamoDB 테이블이 지정되면 공유된다. 비어 있으면 로컬 개발용 메모리 저장소를 사용하며 재시작 시 로그아웃된다. DynamoDB TTL 삭제는 비동기이므로 API는 모든 읽기에서 만료 시각을 직접 검사한다.
- 세션은 최장 1시간이고 Access 토큰 만료를 넘지 않는다. 고객 TOTP 등록용 Access 토큰과 관리자 인증 챌린지 세션은 브라우저에 노출하지 않고 공유 저장소에 만료 시각과 함께 저장한다. 등록 키는 등록 요청의 응답으로만 전달하고 저장하지 않는다. 관리자 화면의 비밀번호와 TOTP 값은 Cognito 인증 요청에만 사용하고 로그나 저장소에 기록하지 않는다. 공개 배포에는 HTTPS가 필수다. 프로젝트 관리자의 `POST /api/admin/users/{subject}/revoke-admin`과 `POST /api/admin/users/{subject}/suspend`는 CSRF를 확인한 뒤 공유 저장소의 차단 상태와 권한 버전을 변경한다. 기존 세션은 다음 API 요청부터 거부되며 새 관리자 로그인 또는 이용 중단 계정의 로그인도 거부된다. 이 조치는 애플리케이션 접근을 차단하며 Cognito 그룹·계정 상태 자체를 변경하지 않는다.
- 보호 API 요청마다 Cognito의 현재 계정 활성 상태를 확인하고 관리자 요청에는 현재 그룹도 확인한다. Cognito 호출에 실패하면 접근을 허용하지 않는다. 이 방식은 요청마다 Cognito API 호출과 지연을 추가하므로 부하 시험에서 조정해야 한다. 갱신은 별도 KMS 키·역할 권한과 실제 Cognito 설정의 검증이 필요하며 실제 공개 서비스용 인증 완료로 취급하지 않는다.
- 무료 예시 API는 공용 합성 자료만 읽기 전용으로 반환한다. 합성 조리작업·평가와 시연용 티어 전환 신청은 별도 고객 범위에 저장한다. 매장별 범위·권한 모델과 무료 AI 모델의 자동 제공은 후속 기능이다.

세션 갱신은 `FOODTECH_AUTH_REFRESH_KEY_ARN`과 `FOODTECH_ENVIRONMENT`가 구성된 경우에만 새 로그인부터 활성화된다. 갱신 토큰은 서버에서 AWS Encryption SDK의 key commitment와 세션별 암호화 컨텍스트로 보호한다. 고객·관리자 화면과 콤비 합성 수집은 만료 전에 CSRF 보호 갱신을 요청한다. 갱신 중 로그아웃·경쟁을 조건부 쓰기로 차단하고 최대 세션 수명은 로그인부터 8시간이다. 브라우저 재접속 시 액세스 토큰이 만료되어도 유효한 서버 세션과 권한이 있으면 캐시하지 않는 CSRF 문맥을 받아 갱신한다. 서버 세션의 최대 수명이 끝나거나 권한이 회수되면 재로그인이 필요하다. 로그아웃은 서버 세션을 먼저 삭제하고 Cognito 토큰 회수를 시도하며 `cognitoTokenRevoked`로 성공 여부를 구분한다. 갱신 중 세션이 삭제되어 새 토큰 저장에 실패하면 해당 토큰의 회수도 시도하지만, 네트워크·프로세스 장애 중 회수 성공은 보장하지 않는다. 기존 시험 Cognito 고객 계정과 개발 DynamoDB·KMS를 사용해 로그인, 갱신, 갱신 후 세션 조회, 토큰 회수와 로그아웃 후 접근 거부를 확인했다. 같은 시험 계정에 관리자 그룹을 일시 부여해 비밀번호·TOTP 로그인 이후 동일한 갱신·회수를 확인하고 관리자 권한 제거를 검증했다. 해당 시험 App Client는 토큰 회전이 꺼져 있었으므로 회전 활성 상태, 전용 KMS 키 정책과 배포 역할은 아직 실검증하지 않았다. KMS 시험에는 기존 개발 키를 임시 사용했으며 배포 키나 역할을 검증한 결과는 아니다. 설정이 없거나 이전 세션이면 기존 만료 동작을 유지한다.
- 2026-11-01 AWS Free Plan의 시험용 Cognito User Pool에서 고객 가입·이메일 확인·Authorization Code/PKCE 토큰 교환·고객 세션·관리자 그룹 거부·로그아웃 후 API 거부를 확인했다. Cognito 관리형 로그인 v2는 시험 계정에서 동작했다. 시험 리소스는 아직 CDK 관리 대상이 아니다.
- 같은 시험 계정으로 DynamoDB 공유 저장소를 연결해 다시 로그인했다. 세션 생성, API 프로세스 재시작 후 로그인 유지, 로그아웃 후 세션 제거를 실제 AWS 테이블에서 확인했다.
- 시험 Pool의 관리형 로그인은 TOTP를 완료해도 토큰에 `acr`·`amr`를 넣지 않았다. 관리자 App Client의 직접 인증 경로에서 Cognito `SOFTWARE_TOKEN_MFA` 챌린지 성공 후 관리자 화면 진입을 확인했다. 시험용 관리자 그룹을 즉시 회수하고 다음 화면 요청에서 접근이 거부되는 것도 확인했다. Pool MFA는 `OPTIONAL`을 유지한다.

## 돈까스 합성 조리작업 첫 흐름

`/api/customer/cooking-jobs`는 고객 세션의 `subject`에서 저장 범위를 만들고 상태 변경 요청마다 CSRF와 기대 `version`을 검사한다. 첫 범위는 합성 튀김기 `synthetic-fryer`의 돈까스 작업이다. 생성, 승인된 수동 상태 전이, 심부온도 안전 확인, 안전 이상·해제, 완료 품질평가, 평가 이력과 재조리 연결을 제공한다. 연결된 합성 배치의 표준화된 온도값에 대해서는 자동 공정판정을 수행한다. 고객이 `PROCESS_FAILURE_DETECTED`를 임의로 제출하는 API는 제공하지 않는다.

`POST /api/customer/ai/cooking-chat`은 고객이 소유한 조리작업의 버전·합성 메뉴·작업/안전/공정/시간 상태와 유효한 품질 합격 여부만 구조화된 사용자 메시지에 담아 로컬 모델에 전달한다. 원본 표본·소유자 ID·자유 메모는 전달하지 않는다. 차단되었거나 안전 버전이 맞지 않는 평가는 미확인으로 전달하고, 늦은 수집값의 파생 판정이 있으면 해당 판정과 작업 버전 변경 여부를 함께 표시한다. 이 상담은 조회 시점의 설명이며 설정값 검증·안전 판정·후보 레시피 생성을 수행하지 않는다. 시스템 역할 분리는 모델 출력을 안전한 권고로 보장하지 않으므로 운영자가 검토해야 한다.

2026-11-21에는 `AWS_PROFILE=foodtech FOODTECH_OLLAMA_BIN=<ollama 실행파일> .venv/bin/python tests/live/cooking_context_ollama_check.py`로 합성 고객 세션·개발 DynamoDB 작업과 실행 기록·실제 루프백 mTLS Gateway·로컬 `llama3.1:8b`를 결합했다. 작업 맥락과 식별자 제외, 응답 저장, 모델 종료 후 실패 기록, 호출 한도 및 시험 항목 정리를 확인했다. 모델 출력의 정확성·안전성, 실제 Cognito·배포 환경과 서버 GPU 성능은 이 시험 범위가 아니다.

돈까스 합성 심부온도 입력은 화면과 API 모두 -273.15~300°C로 제한한다. 범위 밖 입력은 판정이나 작업 버전을 변경하지 않는다. 이 범위는 합성 입력의 기술적 제한이며 식품 안전 허용 범위가 아니다.

안전 확인은 계획 인분마다 독립 탐침의 0~60초 1Hz 합성 시계열 61개를 요구한다. 모든 유효 표본이 `75°C` 이상이면 `PASSED`, 유효 표본 하나라도 미달하면 `FAILED`, 시간축·필수값·교정 유효성이 부족하면 `INCOMPLETE`다. 이상 의심·확인 중·실패에서는 평가를 완료할 수 없다. 의심 해제나 새 안전 확인만으로 기존 합격 평가를 다시 사용 가능하게 만들지 않으며, 새 완료 평가가 필요하다. 작업 상태·안전 상태의 변경과 근거는 `EVENT#...` 이력에 현재 상태 변경과 함께 원자적으로 기록한다.

품질평가는 초기 공통 척도 `tonkatsu-common-v1`의 7개 항목 모두에 1~5점과 관찰 근거를 요구한다. `해당 없음`은 이 첫 척도에 없다. 종합점수는 합계/35×100이며 모든 항목이 3점 이상일 때 합격, 4점 이상일 때 목표 달성이다. 수정·재평가는 사유와 이전 버전을 기록하고 원본을 보존한다. 새 버전과 `ASSESSMENT#CURRENT` 포인터는 같은 DynamoDB 트랜잭션으로 기록하며 작업 `version` 충돌을 거부한다.

`POST /api/customer/cooking-jobs/{id}/tonkatsu-initial-context`는 조리 전 합성 재료 온도·관찰 시각·보관 상태와 기름 용량·교체 후 배치 수·누적 조리량·교체 시각을 선택적으로 기록한다. 값은 `DECLARED_UNVERIFIED`이며 실제 측정이나 안전 판정이 아니다. 배치 버전이 달라지면 이전 값은 현재 권고 근거에서 제외하고, 변경 이력은 별도 사건으로 보존한다. 초기 온도와 교체 시각은 투입 시각보다 늦을 수 없다.
