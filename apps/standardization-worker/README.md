# 첫 표준화 Worker

돈까스 재계산은 같은 스트림 원본 스냅샷에 포함된 유효·경고 표본 중 투입 전 마지막 온도 표본과 투입까지의 간격을 보존한다. 마지막 시각이 중복되면 `AMBIGUOUS`, 표본이 없으면 `NOT_CAPTURED`로 두며 온도를 추정하지 않는다. 선택된 표본의 품질 상태도 보존한다.

FIFO의 `CUSTOMER_RESTATEMENT`는 고객 API가 조리작업에 저장한 동일 요청 ID와 `CUSTOMER_REFRESH` 사유를 다시 확인한 후 처리한다. 전체 원천 스냅샷의 준비·작업 및 원본 버전 조건을 검사하며, 이미 완료된 요청은 멱등하게 반환한다. 데이터가 아직 준비되지 않았거나 버전이 바뀌면 메시지를 삭제하지 않고 재시도한다. 요청은 일반 원천 메시지와 별도 FIFO 그룹을 사용한다. 현재 Worker는 한 메시지에서 오류가 나면 같은 수신 묶음의 나머지 처리도 중단하므로 일시 지연될 수 있다.

돈까스 공정 재계산은 조리 구간의 표준화된 온도 표본에서 첫·최저·최고·마지막 표본값, 160°C 미만·180°C 초과 연속 표본 사이의 관찰 시간 합계와 마지막 저온 표본 복귀 구간을 별도 버전으로 기록한다. 순번 결손이나 5초 초과 간격은 시간 합계와 복귀 구간을 연결하지 않는다. 이는 점 표본 사이의 시간이며 실제 온도·실제 복원시간을 보간하거나 투입 직전 온도를 추정하지 않는다.

공정 재계산은 스트림 버전을 원본 조회 전후에 확인하고 결과·포인터 저장 트랜잭션에서도 같은 버전을 조건으로 검사한다. 원본이 바뀌면 재시도하며 기존 버전이 없는 스트림은 결측 상태를 명시한다. 원본 작성자의 버전 증가 계약을 모두 적용하고 실제 AI 실행 직전에도 원본과 조리작업을 조건부로 확인하기 전까지는 이 값만으로 최신성을 보장하거나 AI 실행을 허용하지 않는다.

공정 재계산은 같은 스트림의 수집 종료 기록과 원본 스냅샷을 건수와 바이트 해시별 중복 횟수까지 대조하고 일치 여부를 파생 결과에 기록한다. 기록이 없거나 원본이 다르면 미일치로 남기며, 일치도 이후 추가 데이터의 부재·입력 전체 완전성·AI 실행 가능성을 보증하지 않는다. 종료 기록이 재계산 이후에 도착한 경우에는 새 재계산이 필요하다.

`jeyuk_bridge.JeyukProcessStream`은 로컬 HTTPS 수집기로 받은 C# 합성 볶음·교반 원표본을 검증하고 승인된 제육볶음 공정판정기로 전달한다. `mockprofile-110`의 AWS 경로에서는 같은 원본을 DynamoDB에서 강하게 읽어 1초씩 판정한다. Worker는 판정 결과와 다음 모니터 상태를 조건부 트랜잭션으로 함께 저장하며, FIFO 재전달은 기존 판정을 재사용한다. 기존 `mockprofile-100` Worker 경로와 키 공간을 분리했다. 명시적으로 연결된 고객 제육볶음 작업이 `RUNNING` 또는 `PAUSED`이면 이 판정을 작업에 기록하고 실패 시 작업을 `FAILED`로 바꾼다. 2026-11-15 개발용 AWS에서 표본 30건을 순서대로 처리해 5초 걸림 경고·30초 실패·작업 실패 전이·마지막 판정의 재전달 재사용을 확인했다. 시험 항목은 정리했다. 수동 안전 검증과 완료 평가는 별도다.

안전 필드가 있는 제육볶음 원표본은 공정판정 상태와 별도로 혼합물 자동 안전 상태를 원자적으로 저장한다. 마지막 재료 투입 완료 다음 초부터 75°C 이상 60초 연속 유지하면 `auto_safety_status=PASSED`와 통과 초를 작업에 기록한다. 2026-11-15 개발용 AWS에서 61개 C# 합성 표본으로 60초 대기·61초 통과, 작업의 `RUNNING`·평가 차단 유지와 재전달 재사용을 확인하고 합성 항목을 정리했다. 수동 육류 탐침 검증과 완료 평가는 아직 연결되지 않았다.

제육볶음 작업 판정을 동반하는 DynamoDB·SQS 검증에는 한 번에 받은 FIFO 메시지 10건의 순차 작업 갱신이 30초 가시성 시간을 넘는 사례가 있어 Worker 수신 가시성 시간을 180초로 조정했다. 이는 개발용 호출 지연을 반영한 초기값이며 부하·장애 시험에서 재조정한다.

SQS FIFO의 원본 참조를 받아 DynamoDB 원본을 강하게 읽고, 원천 스키마 검증 → 값 정규화 → RFC 8785 직렬화 → SHA-256 → 결정적 매핑 → 품질 판정을 수행한다. `python -m foodtech_standardization_worker.aws_flow`은 한 번에 최대 10건을 처리한다.

첫 품질 규칙은 절대영도보다 낮은 온도의 `HARD_LIMIT_EXCEEDED` 격리와 순번 결손·지연 도착 경고다. 정상 레코드만 표준 결과를 갖고, 격리 레코드도 원본 이벤트·불변 평가·Finding을 남긴다. 격리 참조는 별도 FIFO Standardization DLQ로 보낸다. 같은 업무 키의 다른 내용은 원본을 보존하고 `DUPLICATE_KEY_CONFLICT` Finding을 남긴다.

돈까스 공정의 `tonkatsu-temperature-v3`는 수집 중 한 번 관찰한 결손을 이후 정상 표본에서도 유지하고 5초를 초과하는 소수점 간격도 결손으로 감지한다. 결손 직후 연속 온도 타이머는 새 구간으로 시작한다. 이전 v1·v2 기록에서 이어지는 작업은 과거 결손 이력을 확인할 수 없으므로 `gap_history_verified=false`와 공정 경고로 유지한다. 원본 재계산은 별도 파생 결과를 만들며 기존 작업 이력을 고치지 않는다. v3의 이력 검증은 최초 관찰 이전이나 마지막 관찰 이후의 누락까지 보증하지 않는다.

실제 C# Mock HTTPS/OAuth 응답의 역순·격리 실저장은 `AWS_PROFILE=foodtech .venv/bin/python tests/live/mock_quality_dynamodb_check.py`로 확인한다. .NET 10 Mock을 Release로 빌드하고 `dotnet`을 PATH에 둬야 한다. 스크립트는 공유 개발용 FIFO 큐 두 개가 비어 있을 때만 시작하며, 고유 합성 배치를 만든 뒤 원본·순번·품질·DLQ 결과를 확인하고 시험 항목을 삭제한다. 2026-11-15 개발용 DynamoDB·SQS에서 도착 순서 `1, 3, 2`가 `1, 2, 3`으로 복원됐고 품질은 `VALID, VALID, QUARANTINED`, 격리 사유는 `HARD_LIMIT_EXCEEDED`, DLQ 참조는 1건이었다. 합성 항목 정리도 확인했다. 이는 로컬 Mock·Worker가 개발용 저장소를 사용한 검증이며 배포된 Task 역할·운영 부하 검증은 별도다.

환경 변수는 `FOODTECH_DATA_TABLE`, `FOODTECH_ORDERED_QUEUE_URL`, `FOODTECH_STANDARDIZATION_DLQ_URL`이다. 이번 테이블은 최소 시험용 물리 배치이며 전체 승인 ERD의 테이블 정의를 대체하지 않는다. 데이터별 soft limit, 재처리 승인 절차, 집계 파생 버전과 운영 보존기간은 이후 계약이다.

`FOODTECH_COOKING_TABLE`을 추가하면 고객이 명시적으로 연결한 합성 수집 배치에 대해 첫 돈까스 온도 공정판정을 기록한다. Worker는 표준화 평가를 영속 저장한 뒤 조리작업 테이블의 바인딩을 강하게 읽고, 정상·경고 표본만 규칙에 전달한다. 5초보다 긴 간격이나 `DATA_GAP`은 연속시간을 끊으며 격리·중복·늦은 이벤트는 현재 판정에서 제외한다. 같은 수신 ID의 재시도는 사건 키와 조건부 트랜잭션으로 한 번만 반영한다. 공정 실패가 확정되면 작업을 `FAILED`로 변경하되 장비에는 어떤 명령도 전송하지 않는다. 개발용 AWS 테이블·큐에서 이 경로의 실저장 결과를 확인했다. 배포된 Worker 실행 역할의 권한·성능은 후속 검증 대상이다.

`LATE_AFTER_GAP` 평가가 명시적으로 연결된 조리작업에 도착하면 Worker는 작업이 종료된 뒤에도 조리작업 파티션에 `RESTATEMENT#REQUEST#<ingestion_event_id>`를 조건부로 한 번 기록한다. 요청에는 원본 평가 위치, 순번·시각, 발견 당시 작업 버전과 공정 상태를 담는다. Worker는 표준화 평가를 저장한 직후 이 요청의 파생 계산을 실행한다. 조건부 저장 충돌 등으로 계산을 완료하지 못하면 처리 오류로 남겨 SQS 메시지가 재전달될 때 다시 시도한다. 현재 작업 상태·판정과 과거 평가를 변경하지 않는다. 이 요청만으로 늦은 이벤트가 현재 공정판정에 반영되었다고 간주하면 안 된다.

수동 재실행이 필요하면 `python -m foodtech_standardization_worker.process_restatement <job_pk> <ingestion_event_id>`를 사용한다. Worker와 이 명령은 `FOODTECH_COOKING_TABLE`과 `FOODTECH_DATA_TABLE`을 사용한다. 요청이 지정한 수집 배치의 원본을 강하게 조회하고, 적용된 공정 사건과 완료된 늦은 이벤트 요청을 합쳐 최대 1,000건의 표준화 평가를 확인한다. 아직 평가가 없는 원본이 있으면 요청을 완료하지 않고 재시도한다. 종료 후 작업에 적용되지 않은 정상 표본도 조리 구간 안이면 발생 시각순 재계산에 포함한다. 조리 구간 밖·격리·중복·비가동 표본은 사유와 함께 제외하며 다른 배치는 오류로 처리한다. 원본 수신 순서의 gap 표식은 재사용하지 않고 발생 시각과 순번 간격으로 다시 판정한다. 결과는 입력 목록·제외 사유의 RFC 8785/SHA-256 해시를 키로 하는 `DERIVED_ONLY` 기록이다. 결과 저장·요청 완료·`PROCESS#LATEST_RESTATED` 포인터 전환을 하나의 트랜잭션으로 처리하고 포인터 버전 조건으로 동시 전환을 검사한다. 같은 요청의 재실행은 `ALREADY_COMPLETED`다. 이 입력 목록은 조회 시점에 발견한 원본의 스냅샷이다. 현재 작업의 `META`·품질평가 `ASSESSMENT#CURRENT` 포인터는 변경하지 않는다. 파생 결과가 바뀌면 작업에 기록된 `AGGREGATE#DEP#` 항목으로 영향을 받는 선택 표본 그룹을 찾고 업무 API의 집계 계산식을 재사용해 새 불변 결과와 그룹의 최신 결과 포인터를 기록한다. 집계 갱신이 실패하면 요청 재시도 시 다시 실행한다.

최신 파생 결과가 생긴 뒤 같은 배치의 적격 일반 표본이 도착하면 Worker는 최신 결과의 입력 목록을 확인한다. 새 표본이면 `FOLLOWUP_SAMPLE` 재계산 요청을 수신 ID당 한 번 만들고 새 불변 결과와 최신 포인터를 기록한다. 작업이 끝났어도 원래 공정판정을 변경하지 않는다. 계산 실패 시 SQS 메시지를 삭제하지 않아 저장된 표준화 평가로 재시도한다. 동일 표본의 재전달이나 이미 최신 결과에 포함된 표본은 추가 결과를 만들지 않는다. 격리·중복·비가동 표본은 이 자동 갱신의 트리거가 아니다.

재계산 결과의 `observation_coverage`는 적격 표본의 최초·최종 시각과 건수, 기록된 조리 시작부터 첫 표본까지 및 마지막 표본부터 인양까지의 시간을 마이크로초로 기록한다. 조리 경계가 없으면 해당 값은 `null`이다. 표본 사이 결손은 별도로 표시한다. 이 값은 전체 원본 존재나 조리 구간의 완전성을 보증하지 않으며, 이전 결과에는 없을 수 있다. 입력 해시에 공정 규칙과 관찰 범위 계산 버전을 포함해 규칙이 바뀐 결과를 구분한다.

고객 업무 API가 기록한 두께·조리시간 상태는 공통 규칙으로 온도 상태와 합산한다. 온도 표본이 들어와도 기존 두께 경고를 지우지 않는다. 2026-11-14 기존 개발용 AWS 조리작업 테이블에서 정상 온도 표본의 `INSUFFICIENT_DATA`가 300초 완료 기록 후 종합 `NORMAL`로 바뀌고, 260초 조기 인양은 온도가 정상이더라도 `FAILED`가 되는 것을 확인했다. Worker 갱신이 완료 기록 직전에 들어오면 오래된 버전의 완료 요청은 409로 거부되고 재조회 후 재시도에서 결합 판정이 유지됐다. 완료 후 추가 표본은 현재 공정판정에 반영하지 않는다. 이 시험은 표준화 전단·SQS를 통과시키지 않고 Worker의 조리작업 반영 경계를 직접 사용했다.

온도·두께·실제 조리시간의 후속 결합과 늦은 이벤트 요청 저장 검증은 `AWS_PROFILE=foodtech FOODTECH_COOKING_TABLE=foodtech-cooking-jobs-dev .venv/bin/python tests/live/process_time_worker_dynamodb_check.py`로 재실행한다. 2026-11-14 개발용 DynamoDB에서 종료된 작업의 요청이 `PENDING`으로 한 번만 저장되고 재전달 시 기존 요청이 유지되며 현재 판정이 바뀌지 않는 것을 확인했다. 합성 작업·바인딩 파티션 4개를 생성하며 종료 시 모두 삭제하고 잔존 0건을 확인한다. 실제 AWS 요청 비용이 발생할 수 있다.

파생 결과 실저장은 `AWS_PROFILE=foodtech FOODTECH_COOKING_TABLE=foodtech-cooking-jobs-dev FOODTECH_DATA_TABLE=foodtech-data-flow-dev .venv/bin/python tests/live/late_restatement_dynamodb_check.py`로 확인한다. 2026-11-14 개발용 DynamoDB에서 늦은 표본이 순번 간격을 채운 첫 `NORMAL` 파생 결과를 만든 뒤 일반 표본이 추가되어 새 파생 결과와 포인터 버전 2를 만드는 것을 확인했다. 합성 표본 4건이 포함됐고 이전 결과와 현재 작업은 유지됐다. 시험에 사용한 합성 파티션 7개를 정리한다. 실제 SQS 전달·재시도와 배포된 Worker 실행 역할은 이 시험 범위에 포함되지 않는다. 실제 AWS 요청 비용이 발생할 수 있다.

실제 FIFO 전달·재시도는 `AWS_PROFILE=foodtech FOODTECH_DATA_TABLE=foodtech-data-flow-dev FOODTECH_COOKING_TABLE=foodtech-cooking-jobs-dev .venv/bin/python tests/live/late_restatement_sqs_retry_check.py`로 확인한다. 2026-11-14 개발용 큐가 비어 있음을 확인한 뒤 합성 늦은 이벤트 한 건을 전송하고, 첫 파생 계산에 일시 충돌을 주입했다. Worker가 메시지를 삭제하지 않아 SQS가 재전달했고, 저장된 표준화 평가를 재사용하여 요청을 `COMPLETED`로 바꾸고 `NORMAL` 파생 결과를 기록했다. 현재 조리작업 판정은 유지됐으며 시험 메시지와 합성 DynamoDB 항목을 정리했다. 배포된 Worker 실행 역할과 실제 서비스 부하 조건은 별도 검증 대상이다. 실제 AWS 요청 비용이 발생할 수 있다.


### 중복 키 v2 전환

공통 중복 키 v2는 `sourceId`, `deviceId`, `schemaVersion`, `recordId`를 길이 접두 형식으로 구분한다. 공통 키 함수는 recordId가 없는 경우 원천·장비·순번·UTC 정규화 발생시각을 사용하는 별도 fallback 영역도 정의한다. 현재 합성 프로파일의 스키마는 recordId를 계속 필수로 요구하므로 fallback이 해당 프로파일의 입력 검증을 우회하지는 않는다.

v1 키는 읽기 전용으로 보존한다. v2가 없고 v1이 있다면 최초 평가와 원본의 v1 키·내용 해시를 강하게 읽어 검증한 후 같은 장비일 때만 최초 수신과 해시를 v2에 연결한다. 원본이나 평가가 없거나 일치하지 않으면 처리를 중단한다. 중단된 같은 최초 수신의 재시도는 그 입력을 검증해 복구한다. 기존 평가를 덮어쓰거나 기존 오판정을 자동 재처리하지 않는다.

**배포 전 전환 조건:** 구버전 Worker의 소비를 중단하고 처리 중인 메시지가 정리됐는지 확인한 후 신버전만 실행한다. 구버전과 신버전의 동시 처리나 롤백 중 신규 쓰기는 보장하지 않는다. 실환경 데이터 이전 및 다중 Worker 경쟁·롤백 검증은 아직 수행하지 않았다.

조리작업 연동 Worker는 `FOODTECH_COOKING_TABLE`과 함께 `FOODTECH_AUTH_TABLE`을 반드시 설정한다. 제육·돈까스 작업에 새 공정 결과를 저장하거나 돈까스의 늦은 이벤트 재평가 요청을 만들 때 인증 테이블의 정지·삭제 잠금 부재를 동일 트랜잭션으로 확인한다. 잠금으로 충돌하면 오류를 전파해 현재 SQS 메시지를 삭제하지 않고 재시도·DLQ 경로에 남긴다. 잠금 장기화 시 큐 정리와 사용자 삭제 절차는 아직 구현되지 않았다. 이 보호는 두 메뉴의 현재 판정과 돈까스 재평가 요청 생성에 적용되며 재평가 결과·집계 등 다른 Worker 쓰기 경로는 별도 구현이 필요하다. CDK에 인증 테이블 `ConditionCheckItem`을 추가했으나 아직 배포·실제 Worker 역할 검증을 수행하지 않았다. 개발 시험에는 `FOODTECH_AUTH_TABLE=foodtech-auth-sessions-dev`를 설정한다.

돈까스 재평가의 새 결과·요청 완료·포인터 및 오래된 고객 요청의 `STALE` 전환은 인증 테이블의 정지·삭제 잠금을 같은 트랜잭션에서 검사한다. 개발 DynamoDB에서 합성 대기 요청을 잠근 뒤 두 쓰기가 차단되고 잠금 해제 후 재평가되는 것을 확인했다. 완료된 재평가의 재전달이 호출하는 집계 갱신과 기타 파생 쓰기에는 아직 별도 잠금이 필요하다. `FOODTECH_AUTH_TABLE`과 권한을 설정하지 않으면 재평가 구성요소는 시작되지 않는다.
