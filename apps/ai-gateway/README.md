# AI Gateway 첫 실행 정책 경계

로컬 권고 전환 동의의 부모 실행에 조리작업 ID와 버전이 지정된 경우 고지와 새 실행에도 같은 값을 보존한다. 고지 후 부모의 연결이 바뀌면 확인을 거부한다. 이는 기록의 연결 검사이며, 실제 권고 실행 전 조리작업 최신 상태와 근거를 다시 검증해야 한다. 기존 연결 없는 실행도 읽을 수 있다.

고객이 이전 합성 조리작업을 선택하면 업무 API는 현재 조회한 이전 작업의 ID와 버전을 요청·전환 고지·새 실행에 함께 연결한다. 고객 간 접근과 작업 버전 변경은 거부한다. 이 기록은 선택한 비교 근거를 식별할 뿐 실제 직전 작업임을 증명하거나 AI 실행을 허용하지 않는다.

제육볶음 원천 수집 완료 기록과 원본이 일치한 경우, 현재 작업과 선택한 이전 작업의 관찰 원천 버전도 요청·전환 고지·새 실행에 보존한다. 업무 API는 요청과 전환 확인마다 버전을 다시 읽어, 변경이나 완료 기록 불일치가 감지되면 거부한다. 이 검사는 조회 시점의 변경을 감지하며 AI 호출 직전의 최종 검증과 직전 작업 확인을 대체하지 않는다.

제육볶음 로컬 권고 실행 경계에는 서버 저장 실행 기록을 기준으로 작업 소유자·작업 버전과 두 원천 버전을 직접 강하게 읽는 검사기를 추가했다. 검사기가 없거나 검사에 실패하면 모델을 호출하지 않고, 호출 중 버전이 바뀌면 결과를 폐기하고 실패로 기록한다. 이 검사는 원본의 완전성, 직전 작업 여부나 레거시 작성자의 추적 누락을 증명하지 않는다. 검사기는 명시적으로 전달받은 DynamoDB 리소스만 사용하며 Gateway의 기본 장기 실행 역할로 자동 연결하지 않는다. 리소스를 전달했다는 사실만으로 고객별 권한 범위를 증명하지 않는다. 신뢰 가능한 고객별 자격증명 발급 및 검증과 완전한 근거 승인 경로가 아직 구현되지 않아 공개 실행 경로는 없다. 개발 DynamoDB에서는 개발자 세션의 합성 항목으로 일치·원천 변경 거부와 시험 항목 삭제를 확인했으며 배포 역할은 검증하지 않았다.

검사기는 배치의 역방향 `BINDING`이 같은 고객 작업을 가리키는지도 확인한다. 배치 키 자체에는 고객 식별자가 없으므로 이 애플리케이션 검사만으로 AWS의 고객 간 접근 격리가 완성되는 것은 아니다. 배포 역할에 전체 테이블 읽기 권한을 추가해 해결하지 않으며 고객별 신뢰 경계와 접근 범위 검증이 남아 있다.

각 배치의 전체 합성 원본과 수집 완료 기록의 순서·건수·해시도 비교한다. 개발 DynamoDB에서 버전은 그대로 둔 원본 변경이 감지되는 것을 확인했다. 이 비교는 수집된 원본의 일치 여부이며 센서 유효성이나 직전 작업 여부까지 승인하지 않는다. 고객별로 제한된 `GetItem`·`Query` 권한의 발급과 실검증이 필요하며 전체 테이블 권한은 부여하지 않았다.

작업·역방향 연결·원천 버전을 각각 강하게 두 번 조회해 조회 중 변경을 감지한다. 여러 항목의 조회가 원자적 스냅샷이 되는 것은 아니며, 마지막 조회 후의 변경과 버전을 지키지 않는 이전 작성자까지 배제하지 못한다.

합성 제육볶음 원천 표본은 작업의 실제 투입·인양 시각과 조리시간에 걸쳐 1초 간격으로 빠짐없이 존재하는지, 선택한 이전 작업이 현재 작업 전에 시작해 끝났는지 확인한다. 이 검사는 시간축의 일치와 순서만 확인하며 안전성이나 선택한 작업이 실제 직전 작업인지까지 증명하지 않는다.

개발용 DynamoDB에서 합성 이전 작업 ID·버전의 전환 고지·실행 기록 연결과 동의 재사용 거부를 확인했다. 활성 합성 Tier 1 모델도 미검증 근거에서는 호출하지 않고 사용량이 유지됨을 확인한 뒤 시험 레코드 14건을 삭제했다. Cognito·배포 역할과 실제 모델 실행은 이 검증의 범위에 포함되지 않는다.

`POST /internal/ai/recipe-requests`는 신뢰된 업무 API에서 확인한 합성 조리작업 ID·버전으로 Tier 1 권고 요청을 기록한다. Tier 1 모델이 미설정이면 실행 가능한 모델로 위장하지 않고 차단 사유를 반환한다. 사용자에게 별도로 고지하고 명시적 동의를 받으면 로컬 전환 실행 기록을 생성할 수 있으나 이 경로는 모델을 호출하지 않는다. 서버의 `FOODTECH_RECIPE_TIER1_MODEL_ID`로 등록된 Tier 1 모델을 지정하면 해당 모델의 정책 차단 사유를 표시하며, 정책이 허용되어도 신뢰 가능한 조리 근거가 연결되기 전에는 권고 실행을 차단한다. 실제 권고 실행과 외부 호출의 동의·비용 연결은 아직 구현되지 않았다. 전환 고지와 확인에는 같은 조리작업 ID·버전이 필요하다. 개발용 DynamoDB 합성 시험은 미설정 모델 상태의 트랜잭션도 검증한 후 시험 항목을 삭제한다.

`foodtech_ai_gateway.policy.GatewayPolicy.authorize`는 서버가 보관한 실행 ID만 입력받아 실행 가능 여부를 판단한다. 모델 ID, 자격증명 ID, 동의 여부, 예상 비용과 tenant 범위는 신뢰된 Registry에서 다시 읽는다. 호출자는 인증된 업무 API 서비스와 tenant 범위여야 한다. HTTP 헤더 문자열만으로 `Caller`를 만들면 안 된다.

현재 검사는 다음을 포함한다.

- 모델의 회귀검증·명시적 승인·활성화, 커스텀 모델의 승인 주체
- 기능별 Tier와 고급 추론의 자동 다운그레이드 금지, 저등급 새 실행의 고지·동의 연결
- 외부 모델의 tenant 소유·공급자 일치·사용 가능한 자격증명 버전, 민감정보 로컬 전용 및 외부 전송 승인·동의
- 사용자·공급자·프로젝트의 예상 비용 한도와 호출 잔여량, 일반 작업의 가용한 로컬 기본 모델 fallback

`DynamoRegistry`는 실행·모델·자격증명 메타데이터·동의·월별 한도를 별도 DynamoDB 테이블에 저장한다. `EXEC#<실행 ID>`를 기본 키로 직접 `GetItem`하며 일관된 읽기를 사용한다. 자격증명 레코드에는 `vault:` 참조만 저장하고 키 원문·암호문은 저장하지 않는다. 한도는 `YYYY-MM` 기간의 tenant, provider, project 세 범위로 관리한다. 관리 주체가 각 기간의 레코드를 먼저 생성해야 하며 모든 수정자는 `version`을 증가시켜야 한다.

`GatewayService.prepare(인증된 Caller, 실행 ID)`는 서버 저장 기록을 다시 읽고 정책 판정 후, `PENDING -> RESERVED` 상태와 세 범위의 예상 비용·호출 잔여량을 DynamoDB 트랜잭션 하나로 갱신한다. 모델·자격증명·동의 기록의 읽은 버전도 같은 트랜잭션에서 확인한다. 선택된 로컬 fallback은 원 실행에 임의 적용하지 않고 새 실행 생성을 요구한다. `finish`는 `RESERVED -> SUCCEEDED/FAILED`와 실제 비용 차액 정산을 하나의 트랜잭션으로 처리한다. 예약된 호출 수는 시도 후 복구하지 않는다.

직접 내부 HTTP의 첫 구현에는 mTLS를 사용한다. `python -m foodtech_ai_gateway.serve`는 loopback HTTPS에서 서버 인증서·키와 **업무 API 전용 CA**를 요구하고, 클라이언트 인증서가 없으면 TLS 단계에서 연결을 거절한다. 앱의 내부 경로도 전용 mTLS 실행기와 HTTPS가 아니면 거절한다. 임의의 신원 헤더를 인증 근거로 사용하지 않는다. 서버 인증서의 SAN에는 `127.0.0.1`을 넣고 업무 API의 클라이언트 인증서만 전용 CA로 서명한다. 개발용 인증서·키는 저장소 밖에서 관리한다. 향후 배포 진입 계층에서 IAM 인증이 가능하면 이 경계를 재검토한다.

`POST /internal/ai/executions`는 인증된 업무 API가 전달한 tenant 범위에 `GENERAL_GUIDE`·`llama3.1:8b` 로컬 실행을 생성한다. `POST /internal/ai/executions/{execution_id}/invoke`는 요청의 실행 ID로 기록을 다시 읽고 정책·한도 예약 후 로컬 실행은 loopback Ollama `/api/generate`에 `stream=false`, `num_ctx=4096`으로 요청한다. 이 일반 경로는 외부 모델에 임의 프롬프트를 전달하지 않는다. 결과 또는 정규화된 실패 코드를 `RESULT` 항목과 종료 상태·실제 비용 정산에 함께 기록한다. 프롬프트 원문은 레지스트리에 넣지 않는다. 결과 원문에는 90일 TTL을 설정했으며 정해진 시점의 Hard Delete 보장은 별도 삭제 작업에서 구현해야 한다.

필수 환경변수는 Gateway의 `FOODTECH_AI_REGISTRY_TABLE`, `FOODTECH_GATEWAY_SERVER_CERT`, `FOODTECH_GATEWAY_SERVER_KEY`, `FOODTECH_GATEWAY_BUSINESS_CA`와 업무 API의 `FOODTECH_GATEWAY_URL`, `FOODTECH_GATEWAY_CA`, `FOODTECH_BUSINESS_CLIENT_CERT`, `FOODTECH_BUSINESS_CLIENT_KEY`다. Gateway의 `FOODTECH_OLLAMA_URL` 기본값은 `http://127.0.0.1:11434`이며 loopback URL만 허용한다. 현재 월의 tenant·ollama provider·project 한도와 승인된 `llama3.1:8b` 모델 레코드를 먼저 준비해야 실행된다.

서버 배포 시 Ollama는 Gateway가 접근하는 같은 호스트의 loopback에서 실행하는 첫 계약이다. 서버의 GPU 드라이버·VRAM·실제 사용 가능 메모리, 4K context의 모델 적재 여부, CPU offload, 동시 요청·대기열·OOM·p95 지연을 서버에서 재검증한다. 승인된 최소 목표인 전용 GPU VRAM 8GB 이상은 서버 선정 기준이며, 개발 PC의 성공 여부를 서버 성능 증거로 대체하지 않는다. 서버가 별도 AI 호스트를 써야 한다면 loopback 제한을 해제하기 전에 내부 전송 인증·네트워크 경계를 다시 설계한다.

2026-11-06 개발 PC에서 Ollama 0.40.15와 `llama3.1:8b`를 실제 실행했다. GTX 1650 Ti 4GB의 4K context 적재는 Ollama 표시상 GPU 83%·CPU 17%였고 첫 합성 한국어 요청은 모델 적재를 포함해 96.2초, 출력 78토큰이었다. 이는 단일 로컬 기능 확인이며 서버의 지연·처리량·품질 기준이 아니다. 첫 흐름의 출력 상한은 128토큰, Ollama 호출 timeout은 180초, 업무 API의 Gateway timeout은 195초로 두었다. 서버 GPU에서 실측 후 다시 조정한다.

같은 날 합성 고객 요청을 업무 API HTTP 경로 → 실제 mTLS Gateway → 실제 Ollama → 실행 결과 저장까지 통과시켜 `SUCCEEDED`와 저장 응답 일치를 확인했다. 없는 모델의 실제 Ollama HTTP 오류는 `FAILED / OLLAMA_HTTP_ERROR`로 저장됐다. 이 시험에서는 고객 세션·CSRF를 대역으로, 레지스트리는 메모리 시험 구현으로 사용했다.

2026-11-07에는 [실저장 검증 스크립트](../../tests/live/ai_gateway_dynamodb_check.py)로 같은 업무 API → 실제 mTLS Gateway → 실제 Ollama → 개발용 DynamoDB 레지스트리 경로를 결합했다. 합성 요청의 `SUCCEEDED`와 응답 본문 저장 일치, Ollama 종료 후 `FAILED / OLLAMA_UNAVAILABLE`, 두 실행의 tenant 호출 잔여량 `2→1→0`을 확인했다. 시험 레코드는 삭제했고 테이블 항목 수 0을 확인했다. 재실행 명령은 저장소 루트에서 `AWS_PROFILE=foodtech uv run --no-sync python tests/live/ai_gateway_dynamodb_check.py`다. 스크립트는 로컬 Ollama와 Gateway를 임시 실행하며 AWS 요청이 발생한다. 고객 세션·CSRF는 합성 대역이고, 실제 Cognito 세션·배포된 Gateway 실행 역할·서버 GPU 성능은 아직 검증하지 않았다.

고객 채팅은 검증된 사용자·어시스턴트 턴을 분리해 Gateway로 전달한다. Gateway는 고객이 지정할 수 없는 시스템 메시지를 추가해 Ollama `/api/chat`을 호출하며 잘못된 역할·순서·길이와 시스템 역할 위조를 거부한다. 역할 분리는 프롬프트 주입에 대한 완전한 방어를 보장하지 않는다. 2026-11-20 설치된 `llama3.1:8b`와 로컬 Ollama에서 분리된 메시지로 응답 생성을 확인했다. 해당 시험은 배포 환경이나 실제 고객 세션을 포함하지 않는다.

공통 계약 `foodtech_contracts.recommendation_guard`는 합성 돈까스·제육볶음 후보의 승인된 온도·시간·RPM·하중 경계와 직전 안전 실패·걸림 이후 금지 변경을 검사한다. 필수 증거나 이전 기준이 없으면 `INDETERMINATE`, 위반은 `REJECTED`다. `WITHIN_ENCODED_LIMITS`는 구현된 제한을 통과했다는 뜻이며 전체 안전성이나 권고 승인이 아니다. 이 계약은 아직 모델 출력·업무 증거·후보 레시피 저장에 연결되지 않았으며 기존 상담 답변을 자동으로 검증하지 않는다.

`foodtech_contracts.recommendation_output`은 모델 출력 JSON의 중복·추가 필드, 타입, 크기 및 비유한 수를 검사하고 호출자가 별도로 제공한 신뢰된 이전 기준·증거로 위 제한을 적용한다. 실패·판단 불가·제한 위반은 상태 envelope와 빈 `data`를 반환하며 제한 통과값도 `NEEDS_REVIEW`다. 모델 호출·재시도·Tier 승인·업무 증거 조회·후보 저장 경로는 아직 연결되지 않았다.

## 저장 자격증명과 외부 공급자 첫 실행 경계

이미 승인된 외부 실행 기록의 ID로 들어온 요청은 모델·credential·동의·tenant 소유권·Tier·한도를 레지스트리에서 다시 확인한다. `FOODTECH_CREDENTIAL_VAULT_TABLE`과 `FOODTECH_CREDENTIAL_KMS_KEY_ARNS`가 설정된 Gateway에서만 Vault를 일관되게 읽는다. Vault ref는 `vault:<credential_id>`로 고정하고 credential의 tenant 가명값·provider·환경·허용 KMS 키 ARN과 비교한다. 저장 암호문은 AWS Encryption SDK 4.0.7의 committing signed suite `0x0578`과 `REQUIRE_ENCRYPT_REQUIRE_DECRYPT`로 복호화한다. KMS keyring은 서버가 허용한 키만 사용하고 encryption context의 소유자·목적·환경·버전이 맞아야 평문을 반환한다.

API 키는 호출별 인자로만 전달하고 응답·오류·레지스트리에 기록하지 않는다. 오류는 정해진 코드로만 반환한다. 호출 뒤 `bytearray`는 모든 경로에서 덮어쓰지만 Python 문자열·라이브러리 내부 복사본의 완전 소거는 보장하지 않는다. LiteLLM 비용 목록은 패키지에 포함된 버전으로 고정하여 시작 시 별도 네트워크 조회를 막는다. 공급자 오류 시 실제 청구액을 즉시 알 수 없으므로 예약 비용을 보존한다.

### 신규 고객 무료 체험 한도

로컬 모델 무료 체험의 고객별 월 한도를 자동으로 준비하려면 Gateway에 `FOODTECH_FREE_TRIAL_AUTO_PROVISION=true`, `FOODTECH_FREE_TRIAL_MONTHLY_CALLS`, `FOODTECH_FREE_TRIAL_MONTHLY_USD`를 명시한다. 설정된 달의 첫 고객 요청에서만 tenant 한도를 조건부 생성하며, 동시 요청·재시도 또는 설정 변경으로 기존 잔여량을 재충전하지 않는다. 한도 수치는 시험·시연 운영자가 설정하며 코드가 임의로 정하지 않는다. 내부 레지스트리 단건 삭제는 고객 삭제 요청 잠금을 검사하고 실행의 경우 진행 표식 부재·고객 소유·비예약 상태를 같은 트랜잭션에서 확인한다. 하위 키가 남아 있으면 부모 META 삭제를 거부하며 자격증명은 금고와 함께 처리하는 별도 경로만 허용한다. 이 기능은 인증된 작업자나 전체 탐색, 구버전 작성자의 중지, 백업·복원 후 삭제 검증을 대신하지 않는다.
내부 레지스트리 파티션 삭제는 제한된 페이지의 하위 키를 먼저 제거하고 마지막 페이지에서 부모 META만 남았는지 다시 확인해 제거한다. 도중 충돌 시 페이지 진행 위치를 반환하지 않으므로 같은 범위를 재시도한다. 호출자 인증·구버전 작성자 중단·진행 위치 보호 및 전체 저장소 삭제 검증은 별도다.

2026-11-21 개발 DynamoDB에서 견적 재시도와 무료 한도·실행 예약의 동시성 및 잠금 충돌을 합성 데이터로 검증했다. 별도 로컬 서비스 간 mTLS와 개발 DynamoDB·KMS를 이용한 고객 자격증명 등록, 외부 전송 동의, 합성 공급자 실행과 정산도 확인하고 시험 항목을 정리했다. 실제 공급자 호출과 배포된 서비스 역할은 이 시험의 범위가 아니다.

AI 레지스트리 하위 항목 조회는 페이지 응답 누락, 중복·역순 키, 진행하지 않는 커서와 마지막 키 불일치를 오류로 처리한다. 개발 DynamoDB의 합성 인벤토리·하위 항목 삭제와 정리를 재검증했다. 전체 삭제 완료와 실행 역할 권한은 이 시험이 보장하지 않는다.

AI 기존 기록 인벤토리는 삭제 잠금 아래 스캔한 파티션 후보와 진행 위치를 분리된 암호화 페이지로 저장할 수 있다. 진행 위치 저장이 실패하면 이미 저장한 페이지를 재사용하고, 전체 페이지의 연결·건수와 재조회 시 변조 여부를 확인한 뒤에만 내부 대상자를 반환한다. 개발 DynamoDB·KMS에서 합성 실행·동의 후보 수집과 정리를 검증했다. 진행 저장기·암호화기는 별도 초안 PR에 의존한다. 스캔은 일관된 스냅샷이 아니며 인증된 호출자, 기존 작성자 중단, 실제 저장소 삭제·잔존·백업 검증을 제공하지 않는다.

내부 AI 파티션 작업자는 암호화된 인벤토리에서 대상을 확인하고 실행·동의·견적·고객 한도의 하위 항목을 페이지별 삭제한 뒤 진행 위치를 저장한다. 응답 유실 후 부모가 이미 없으면 하위 항목과 실행 표식 부재를 잠금 아래 재확인한다. 자격증명은 금고 동시 삭제가 필요해 이 경로에서 중단한다. 검증 대기 상태는 전체 삭제 완료가 아니다. 호출자 인증·기존 작성자 중지·호출 정산 및 실제 역할·백업 검증은 남았다.

자격증명 대상은 암호화 인벤토리에서 확인한 뒤 레지스트리와 Vault의 소유·참조·가명 메타데이터를 대조해 금고 ARN과 함께 암호화된 삭제 준비 기록으로 저장한다. 응답 유실 시 같은 기록을 복구할 수 있으나 이 준비 단계는 금고를 삭제하지 않는다. 실행 중 호출 정산 및 이전 예약 전체 확인, 삭제 직전 메타데이터와 잠금의 재검사, 실제 삭제 작업자와 역할 검증은 아직 필요하다.

고객 잠금 확인 전후에 활성 실행 표식 파티션을 강한 일관성으로 한 건 조회해 `PRESENT` 또는 `CLEAR`를 관찰할 수 있다. 개발 DynamoDB에서 합성 표식의 존재·해제와 다른 요청 잠금 거부를 확인했다. 이전 예약에 표식이 없을 수 있고 구버전 작성자가 잠금을 따르지 않을 수 있으므로 `CLEAR`만으로 호출 종료나 삭제 가능을 보장하지 않는다.
